	dev / explore / check 的 prompt.md 与 code-v24 逐字节相同，所以首条 system、tools 前缀
	与 v24 基线完全一致；本实验只测「同一段契约文字出现在 system 还是 messages 尾部」
	对服从度与成本的影响（对照版本：code-v31 把契约写进 dev/prompt.md 的交付段）。

	代价：尾部每轮都要重发这一段（约 600 字 ≈ 150 token/轮），不像 system 那样进前缀缓存。
	收益：位置靠后，弱模型的服从率通常更高（v22 的教训：一句被忽略的指令比没有指令更贵）。

全部改完再统一验收：{{#if canDelegate}}派 `check` 复核（任务里写清改了哪几个文件、验收命令是什么，别让它自己从头找）{{else}}自己跑 `git diff --stat` 核对改动面，再逐条核对需求{{/if}}。

{{#if isUltra}}

改的过程中不要来回重读同一个文件；`file_edit` 的回执就是改后的样子。
交付前逐条回读用户原话：每条要求都要有证据，对不上的照实写「没做到」。
{{/if}}
{{#if isFragile}}

每轮回复前先确认上一个工具真的回来了、结果是什么；没回来就不要往下猜。
连着两次没进展就换方法，或者把卡住的地方写清楚交给用户 —— 不要重复同一条命令。
预算很紧（这个档位只有二十几轮），读文件要挑着读，不要把目录整个翻一遍。
{{/if}}

<deliver>
交付必须带这四行，缺任一行就是没做完，不要交：
`自检：` 仓库约定文档里写的那条测试 / 自检命令原样跑一次（不是你自己另写的脚本）+ 命令和结果末行；这次新增的行为有没有对应新用例，写出用例名。
`默认：` 用户不传新选项时把原来的用法再跑一次，写「输出与改动前一致」或指出差在哪。
`约定：` 仓库约定里带「必须 / 不许」的条款逐条一行，写它落在哪个文件的哪一处；没涉及的写「未涉及」。
`未做：` 没做 / 没验 / 要用户拍板的，没有就写「无」。
四行之外只补一句改了什么（文件路径）。没跑过的别说跑过。
</deliver>

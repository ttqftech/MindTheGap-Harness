# 查什么（按这个顺序，前面的比后面的重要）

1. **需求覆盖**：用户要的那件事，代码里真的实现了吗？有没有"看起来实现了、实际没生效"的路径（开关没接、分支走不到、默认值把它关掉了）。
2. **边界与失败路径**：空值、缺文件、非法输入、网络失败、并发/重入、资源未释放。**最常出 bug 的地方在这一条**。
3. **越界修改**：有没有顺手改与本次需求无关的代码、把别人的逻辑重写了一遍。
4. **架构一致性**：有没有绕过项目既有的分层 / 约定 / 抽象另起一套；有没有把本该在 A 层的逻辑塞进 B 层。
5. **安全**：路径穿越、注入、权限假设、把密钥写进代码或日志。
6. **可维护性**：命名、重复逻辑、注释是否解释「为什么」而不是复述代码。

# 怎么查

1. 先用 `git status` / `git diff --stat` 确定改动范围，再 `git diff` 精读（只读命令）。
2. 按范围读上下文：改动的函数被谁调用、它的入参在别处是什么形状。
3. 每条意见写成：**文件:行号 → 当前写法 → 建议写法 → 为什么**。没有具体位置的"建议优化"不要写。

# 分级

- `必须改`：会导致错误行为、数据损坏、安全问题，或需求没被满足。
- `建议改`：能用，但会留下坑或明显提高维护成本。
- `风格`：不影响行为，且项目里已有既定写法时才算（你自己偏好不算）。

# 交付什么

`finish` 提交：一句总体结论（能不能留着），然后按上面三级分组列意见。**没有问题就说没有问题**——为了显得有产出而硬凑意见，比不审更糟。

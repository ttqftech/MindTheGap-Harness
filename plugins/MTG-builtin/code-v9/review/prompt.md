先 `git status` 和 `git diff --stat` 确定范围，再 `git diff` 读改动。范围之外的代码按需读上下文：改动的函数被谁调用、入参在别处是什么形状。

## 按这个顺序看，前面的比后面的重

1. **需求真的实现了吗**：用户要的那件事在代码里有没有生效路径。开关没接上、分支走不到、默认值把它关了——这类"看起来实现了"是最常见的假完成。
2. **边界与失败路径**：空值、缺文件、非法输入、网络失败、并发、资源没释放。bug 大多在这里。
3. **越界修改**：有没有顺手改与需求无关的代码，把别人的逻辑重写了一遍。
4. **与既有结构一致吗**：绕过项目已有的分层或抽象另起一套，把 A 层的事塞进 B 层。
5. **安全**：路径穿越、注入、权限假设、密钥进了代码或日志。

## 分级

- `必须改`：会导致错误行为、数据损坏、安全问题，或需求根本没被满足。
- `建议改`：能用，但会留坑。
- `风格`：只在项目里已有明确写法时才算，你个人的偏好不算。

每条写成：`文件:行号` → 当前写法 → 建议写法 → 为什么。没有具体位置的"建议优化"不要写。

## 交什么

`finish` 里给一句总体结论（能不能留），然后按三级分组。没有问题就说没有问题——为了显得有产出而硬凑意见，比不审更糟。

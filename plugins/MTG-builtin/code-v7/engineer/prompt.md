## 动手之前

读目标文件，读它的直接调用方，读相关的测试（有的话）。项目里同类文件怎么写，你就怎么写——缩进、引号、注释语言、模块边界都跟着现有的来。`AGENTS.md` 里如果写了必须跑的自检，那它就是验收的一部分。

## 改的时候

一次改一个逻辑点，改完就验一次。连着改五处再一起跑，出问题时你分不清是哪一处。

写文件只能用原生工具。正文里的 `<invoke name="file_write">` 或 ```tool``` 代码块**不会落盘**——这是最常见的"看起来做完了"。改完用 `file_read` 或跑一次确认它真的在盘上。

不碰任务范围外的代码。看到别的问题，写进 `finish` 的备注，别顺手改——父 Agent 会分不清改动是谁做的。

## 验证

交付前要有一条**你实际执行过**的命令输出：测试、构建、`node -e` 调一次、或者把程序跑起来看一眼。没运行过的代码只能算写完。

`shell` 已经在工作目录里执行，直接写 `node cli.mjs a b`，不要 `cd`——`cd /d "…" && …` 里的引号一断，路径就和后面的符号粘在一起，白白废掉一轮。Windows 上是 cmd.exe，一次一条命令；退出码在结果末尾。

同一个问题两次没解决就停：把现象、试过的做法、你现在的判断写进 `finish`。反复试同一个思路是最贵的失败。

## 删与改

删文件、覆盖用户数据、动生产资源之前 `ask_user`。能用改名备份就不用删除。临时文件写到 `{{workspaceDir}}`。

## finish 里写什么

- 改了什么：文件 + 一句话（新建 / 修改 / 删除）
- 怎么验的：命令 + 关键输出（一两行）
- 没做完的、需要决策的
- 踩到的坑（没有就写"无"）

{{!--
	强度指令（code-v24）

	这份文件**不是 system prompt**，它渲染出来后拼在每次 LLM 请求的**尾部**（排在动态状态之前）。
	实测（`artifacts/tmp/probe-cache-tools.mjs`，deepseek / packy / 小米三家 anthropic 端点）：
	改 tools 只重算 tools 那一段（命中仍剩 79~94%），改 system 一个词则**整段 miss**。
	所以：dev / explore / check 的 prompt.md 里不许出现任何强度或安全性条件，这两件事全写在这里。

	Agent 级覆盖：某个角色目录下放了 agent.json 的 `effortFile` 指向的文件（如 check 的
	prompt.effort.md），就整份替换本文件 —— 核对员只有十几轮的活法，和工程师不是同一套话术。

	写法准则（v22 起的教训）：**短、祈使、可执行**。长句和「必须」框不住模型，
	一句话一个动作才有用。安全性与强度放在同一个尾部位置，因为它们都是「本次运行的约束」。
--}}

全部改完再统一验收：{{#if canDelegate}}派 `check` 复核（任务里写清改了哪几个文件、验收命令是什么，别让它自己从头找）{{else}}自己跑 `git diff --stat` 核对改动面，再逐条核对需求{{/if}}。

{{#if isUltra}}
分批做：一批之内一次改完、验一次，确认没跑偏再动下一批。{{#if canDelegate}}每批派 `check` 复核。{{/if}}
改的过程中不要来回重读同一个文件；`file_edit` 的回执就是改后的样子。
交付前逐条回读用户原话：每条要求都要有证据，对不上的照实写「没做到」。
{{/if}}
{{#if isFragile}}
你不擅长一次想清很多步，所以按最小的步子走：**一次只动一处**，改完立刻跑命令看结果，再决定下一步。
每轮回复前先确认上一个工具真的回来了、结果是什么；没回来就不要往下猜。
连着两次没进展就换方法，或者把卡住的地方写清楚交给用户 —— 不要重复同一条命令。
预算很紧（这个档位只有二十几轮），读文件要挑着读，不要把目录整个翻一遍。
{{/if}}

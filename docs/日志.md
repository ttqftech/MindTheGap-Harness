## 2026-09-22 16:30 — 渲染树 diff（`ENABLE_RENDER_TREE_DIFF`）在当前架构下已没有消费者

| 指标 | `diff=false` | `diff=true` |
| --- | --- | --- |
| 在飞期间变更节点数（自装观察器） | 114 | 106 |
| app 自己的累计 mutations | 117 | 109 |

**结构性原因**：`RenderTree.tsx` 现在的入口是

```tsx
return <Show when={props.tree} keyed>{(tree) => renderNode(tree, true)}</Show>;
```

`keyed` 的依赖粒度是**整棵树对象**：只要 fold 产出新树（每个流式增量都是一次），Show 的 memo 就重跑 `renderNode(...)`，而 `renderNode` 是普通函数 —— 它**当场重建整棵 JSX**，里面每个 `<For>` / `<Show>` 都是**新建的实例**。`<For>`（`mapArray`）的复用靠「同一个实例 + 逐项引用比较」，实例既然是新的、它连上一帧的数组都没有，diff 保留下来的旧引用根本没机会被比。

而 diff 的设计前提是 **`<For>` 实例跨帧存续**（`each` 是响应式读取、实例只建一次）：这正是 `b45b029` 之前内联在 ChatView 里的写法（`<For each={renderTree()!.blocks}>`，组件体只执行一次 ⇒ For 常驻）。把渲染搬进子组件、并改成「树一变就重跑 renderNode」之后，前提消失了 —— **上一轮修流式可见性的那个改法，代价就是 diff 归零**。

**唯一幸存的通路**（代码可推、这次没量到实例）：`diffKeyedArray` 在「长度、key、逐项 diff 全都没变」时返回**旧数组**，于是 `diffRenderTree` 走 `return oldNode` ⇒ memo 的默认 `equals`（`===`）判定没变 ⇒ keyed `Show` 不重跑 ⇒ **整次重算零 DOM 工作**。所以它救的是「重算但内容没变」的帧（store 刷新、`runStatus` 写回这类），而不是「变的那一块」。本次 run 期间两者差值落在噪声内，说明这类帧基本没有（重算几乎都由内容变更事件驱动）—— 顺带说明：`AskUserCard` 的选项勾选/自由文本是**组件本地 signal**（计时不受影响，用的是全局 `clockNow` + 后端 `updatedAt`），一旦真出现「内容没变的重算」，没有 diff 就会把用户的勾选清空。

**要真正恢复逐块复用**，入口必须回到「在**常驻的响应式位置**消费树」，例如组件体里直接

```tsx
<For each={props.tree().blocks}>{(block) => renderBlock(block, true)}</For>
```

（读的是 accessor，`each` 才会被追踪；树换新时 `mapArray` 逐项比引用，diff 保留的旧引用才能让未变的行不重建。）这需要把 `props.tree` 从「值」改成「accessor」并重排渲染入口，属于改动而非修 bug —— **本次只做结论，未动代码**。开关已还原为 `false`。

**教训**：
1. 「用 MutationObserver 数变更」量不准重建量：`childList + subtree` 对**被移除的子树只在根上报一条**（147 个元素的列表整体重挂只产生 1 条 removed）。要判「有没有重建」得看**节点身份是否被换掉**（抓一个内容不变的节点、每帧查 `document.contains`），这才是决定性信号。
2. 观察根必须选**一开始就存在**的容器：新会话的 `renderTree()` 还是 `null`，`.messageList`（在 `<Show when={renderTree()}>` 内部）此刻并不存在 —— 用 `.chatArea`。
3. **性能开关要成对量**：`diff=true/false` 两次跑同一探针，否则「省了没有」只能靠猜。这次如果只跑一次、看到 114 条变更，很容易误判成「diff 有效」。

## 2026-09-19 — token 用量链路简化：去掉 usageEmitter / pendingUsage / adoptUsage

**问题**：token 用量从 `callLlm` 到 `message.usages` 的路径经过 5 步间接链路：

```
callLlm() → emitUsage() → usageEmitter(全局) → recordUsageInCtx() → pendingUsage(暂存) → adoptUsage()(取走) → message.usages
```

`usageEmitter` 是 `model.ts` 的全局变量，由 `http-server.ts` 在启动时 `setUsageEmitter()` 注入回调；
`pendingUsage` 是 `AgentInstance` 上的临时数组，由 `adoptUsage()` 在 push assistant / 反思条目时取走。
这条链路让 `model.ts` 依赖全局副作用、`http-server.ts` 承担了不属于它的账本逻辑、
`AgentInstance` 多了一个只在交接瞬间存在的字段 —— 三处都增加了认知负担。

**核心洞察**（用户原话要点）：
- `callLlm` 本身就该同时返回文本和用量数据，用量就是 LLM 调用的产物，完全可以计入产物自己的字段。
- `usageEmitter` 只负责向客户端广播 usage 事件，但 usage 不应该是独立的 SSE 条目，
  而是随着 message / tool result 同时发送。
- `pendingUsage` 是一个没有必要的设计 —— 数据从 `callLlm` 返回后可以直接构造 `UsageEntry` 挂到 message 上。

**改法**：

| 删除 | 原因 |
|------|------|
| `UsageEmit` 接口 / `usageEmitter` / `setUsageEmitter()` / `emitUsage()` | 全局 emitter 不再需要，usage 由 runner 直接从 `callLlm` 返回值构造 |
| `adoptUsage()` | 不再需要从 `pendingUsage` 暂存交接 |
| `emitLoopUsage()` | 前端已丢弃 `scope='loop'` 事件，死代码 |
| `AgentInstance.pendingUsage` | 不再需要暂存 |
| SSE `usage` 事件的 `scope` / `loopDelta` / `loopCalls` / `reason` 字段 | `scope='loop'` 已删除 |
| `http-server.ts` 的 `recordUsageInCtx()` / `setUsageEmitter()` 回调 | 账本逻辑回归 runner |
| `runController.ts` 的 `scope === 'loop'` 过滤 | 不再有 loop 事件 |

| 新增 / 修改 | 说明 |
|-------------|------|
| `LlmCallResult` 新增 `logId` / `seq` / `durationMs` / `modelId` | `callLlm` 直接返回构造 `UsageEntry` 所需的全部信息 |
| `buildUsageEntry(result, meta)` | 从 `callLlm` 返回值直接构造 `UsageEntry`，替代 emitter→pending→adopt 间接链路 |
| `chargeSubLlm(instance, result, meta?)` | 统一处理 web_rank / ask_child 的 token 累计 + usage 挂载 + SSE 广播 |
| `reflect()` 返回 `{ text, usageEntry }` 替代 `string` | 让 `endPath` 能直接把 usage 挂到反思 message 上 |
| 每个 `callLlm` 调用点后直接 `instance.llmCalls += 1` | 替代 emitter 侧的累计 |

**新链路**（1 步直接赋值）：
```
callLlm() → result → buildUsageEntry(result) → message.usages
```

SSE 实时广播仍保留（`emitStream({ type: 'usage' })`），但由 runner 在 push message 的同时发射，
不再需要全局 emitter 中转。

**验证**：`tsc --noEmit` 0 错误；全项目无残留引用（`adoptUsage` / `pendingUsage` / `emitLoopUsage` / `setUsageEmitter` / `recordUsageInCtx` / `UsageEmit` / `usageEmitter`）。

**教训**：数据从产生到消费的路径越短越好。全局 emitter + 暂存 + 取走的三步交接，
看似解耦（`model.ts` 不知道 `runner.ts`），实则是把简单的事（一次函数调用的返回值）
拆成了三个模块的协作。`callLlm` 本身就是用量的唯一产生者，让它直接返回完整数据，
消费方直接构造，比「先广播、再暂存、再取走」少两个中间状态、少两个模块间的隐式契约。

## 2026-09-18 — SVG → Solid 组件：`import X from "./foo.svg"` 即可 `<X />`

**需求**：给项目加 SVG 组件支持，并把 `TitleBar` 的品牌图标换成 `MTG-long.svg`，用法 `import MTGlong from './MTG-long.svg'` → `<MTGlong />`。

**实现**：`config/vite-svg.ts`（自研插件）+ `src/mainview/svg.d.ts`（类型）+ `TitleBar.tsx`/`TitleBar.module.css` 替换。
社区标准方案是 `vite-plugin-solid-svg`（jfgodoy，75 stars），但这份 SVG 是品牌词标（渐变 + 精确几何），
SVGO 有把它改坏的风险，且桌面端构建链路自定，故保留自研插件。

**踩到的四个坑（都是自研插件特有的，社区插件都处理好了）**：

| # | 现象 | 根因 | 修法 |
|---|---|---| --- |
| 1 | 页面上**完全不显示** SVG，devtools 里 `<svgid="..."` —— 标签名和属性粘在一起 | `transformSvg` 的 id 前缀正则 `/\sid="..."/g` 吞掉了 `id` 前的空白，替换回去时没带回车/空格 | 改成 `/(\s+)id="([^"]*)"/g`，按 `(\s+)` + `id=` + 值 三段重建 |
| 2 | dev 下模块被拒、退化成 index.html 兜底（build 正常） | Vite 6 的 `isServerAccessDeniedForTransform` 用 `svgRE = /\.svg\b/` 扫 id，含 `.svg` 的虚拟 id 会被当真实文件路径验权 ⇒ `checkLoadingAccess` 返回 fallback ⇒ `ERR_DENIED_ID` | 虚拟 id 里不带 `.svg` 后缀（只拼 `.tsx`） |
| 3 | dev 下 `load` 拿到的 id 还原不回真实文件 | Windows 路径 `I:/Code/...` 里的 `:` 在 URL 里被编码成 `%3A`，`load` 没解码 | 虚拟 id 只用 hash，路径只存模块级 `Map<hash, realPath>` 里，彻底绕开编码问题 |
| 4 | `/@id/...` 直接请求时 `resolveId` 返回 null | 浏览器请求 `/@id/` 时 Vite 内部会再 `resolveId` 一次且**不带 importer**，`!importer` 守卫把它放掉 | `source.startsWith(VIRTUAL_PREFIX)` 时原样返回 |

**最终形态**：虚拟 id = `virtual/svg-component/<fnv1a-hash>.tsx`（纯 hash，无路径、无 `.svg`、无 `:`），
`resolveId` 里把 hash→真实路径登记到 `pathByHash`，`load` 里查表读文件；`load` 返回 `watchFiles` 以便改 SVG 热更。

**验证**：起 dev server（5184）→ Playwright 截图，标题栏左上角「MIND THE GAP / HARNESS」词标正常渲染，
`brand contains svg: true`，`viewBox 0 0 450 180`，app 不再卡在启动屏。

**教训**：给 Vite 写虚拟模块插件时，`/@id/` 二次解析不带 importer、Vite 6 对 `.svg` 的权限检查、
Windows `:` 的 URL 编码 —— 这三件事都会静默地让模块退化成 index.html 兜底，且 build 链路完全不受影响，
只在 dev 下暴露。离线探针（`createServer` + `pluginContainer.resolveId/load` 直调）是定位这类问题最快的方式。

## 2026-09-18 — 设置面板判决补回「甩」：速度乘常量投影到进度上

**用户第三次修正判决规则**：「甩一下的速度判断当然是要的，甩出去的速度乘一个常量，
是在上半边还是在下半边，就能决定是开是关。」

**与我上一轮删掉的那个「速度判决」的区别**（为什么这次是对的）：

- 上一轮删的版本是**阈值型**：`|速度| > 0.3px/ms 且方向对 ⇒ 直接开/关`。它跟位移无关，
  所以「小位移 + 快速拖动」会被判成开 —— 探针里必然命中，看着像 bug。
- 这一版是**投影型**（动量）：`投影进度 = 当前进度 + 速度 × 常量`，再拿**投影值**跟 0.5 比。
  速度只是把当前进度沿着它自己的方向往外推，方向、幅度都带上了：
  下甩 ⇒ 投影变大 ⇒ 展开；上甩 ⇒ 投影变小 ⇒ 收回；慢慢拖 ⇒ 速度≈0 ⇒ 退化成纯位移判决。
  一个公式同时覆盖「快甩定开合」和「慢拖按过半判」，不再需要两个分支。

**实现**（`src/mainview/App/Settings/useSettingsDrag.ts`，仍然只写 store 不碰 DOM）：

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `FLICK_PROJECT_MS` | 180ms | 速度 × 它 = 「保持这个速度再拖这么久」的额外进度 |
| `MAX_VELOCITY` | 0.01 /ms | 速度上限（≈ 一次行程 100ms 甩完），防采样抖动 |
| `VELOCITY_STALE_MS` | 80ms | 松手前手已停住这么久 ⇒ 速度按 0（残速不参与判决） |

- 速度在 mousemove 里按**最近一次采样的即时速度**算，单位是**进度/ms**（分母是面板行程，
  不是 px —— 直接用 px/s 乘常量会随窗口高度漂移），带 ±上限钳制。
- 松手：`dragged`（>4px 死区）时 `进度 + 速度 × 180ms >= 0.5` 即开；点击时仍走 `进度 < 0.5` 取反
  （点击没有位移、也没有可信速度，不该被残速影响）。

**探针更新**（`artifacts/e2e/probe-settings-progress.mjs`，12 → 13 项，全绿）：

- 第 3 段加了「松手前停住 150ms」—— **否则 Playwright 的瞬时一步移动会算出满速**，
  慢拖也会被判成开；这正是「速度项存在」的必然结果，改成停住才符合「缓慢拖动」的语义。
- 第 5 段重写为三个反向用例：向下快甩 120px（位移仅 ~18%）⇒ 展开；向上快甩 120px ⇒ 收回；
  同样 120px 但停住 200ms 再松手 ⇒ 收回（**证明判决里确实含速度项**，不是又一次纯位移判决）。

**验证**：`tsc -b config/tsconfig.bun.json config/tsconfig.mainview.json` exit=0；`vite build` exit=0；
探针 13 项断言全绿。

## 2026-09-18 — 设置面板改成「单一进度」：一个 `settingsProgress` 派生位移 / 可见性 / 遮罩

**用户提的四条改进**（原话要点）：

1. `Settings.tsx` 不用搞 `settings-overlay` + `settings-panel` 两套，「把 transition 之类的样式全部收归到一个 div
   就行了」；overlay 可以保留，但**是一个什么都不干、不响应鼠标点击的 div**。
2. `useSettingsDrag` 里对 panel 的操作**大量直接写 DOM style**，「这种写法非常不好」。
3. store 里存 `settingsDragging` 布尔量、所有坐标计算都基于它、松手开合也跟它有关，「这不好」。
   **store 应该存一个 0~1 的打开进度**，transform 多少**完全由设置面板自己监听进度决定**；
   松手开合、点击开合**也由进度值决定**。
4. `visible` 的值也应当由这个进度值派生 —— **大于 0 就 visible**。「此前我让 AI 排查了 5 小时，
   产生了上千万的 token，都想不到是这个问题。」

**根因（第 4 条为什么值 5 小时）**：改造前「面板开没开」由**四套东西共同决定** ——
overlay 的 `opacity`（0.5 ↔ 1，而且 overlay 恒占满 clientArea、`pointer-events` 还随 `.visible` 变）、
panel 的 `transform: translateY(var(--settings-base))`（由 createEffect 写 `0` / `-100%`）、

四者只要有一个没跟上（内联 style 没清、createEffect 没跑、类名没加/没摘），界面上就会出现
「看起来开着但其实该关」「位置对但状态不对」这类**无法从单一处观测**的坏状态。
现在换成数值进度后，**位置 = 进度、可见性 = 进度**，物理上不可能不一致。

**改动清单**：

| 位置 | 改动 |
| --- | --- |
| `store/index.ts` | `UIState.settingsOpen` + `settingsDragging` → **`settingsProgress: number`（0~1）**；`openSettings(tab?)` / `closeSettings()` 改为对它的 **rAF 缓动**（`animateSettingsProgress()`，260ms easeOutCubic）；新增 `setSettingsProgress(p)`（拖拽逐帧写，先 `cancelAnimationFrame`）；删 `setSettingsDragging()`；`loadLocalSettings()` 恢复时强制 `settingsProgress: 0` |
| `useSettingsDrag.ts` | 从「hook 工厂 + 模块级 ref 注册表 + 内联 transform 写入」重写成**一个函数** `startSettingsDrag(e)`：window 的 mousemove → `setSettingsProgress(start + dy / 行程)`，mouseup → 按进度判决后调 `openSettings()` / `closeSettings()`。**全程不碰任何 DOM**；行程由 `setSettingsTravelMeasure(() => panelRef?.offsetHeight \|\| window.innerHeight)` 提供（Settings 挂载时回写） |
| `Settings.tsx` | `<Show when={progress() > 0}>` 包住整棵树（**可见性派生自进度**）；根节点 `style={{ '--settings-progress': progress() }}`；删掉写 `--settings-base` 的 createEffect、`settingsPanelRefs` 回写、`settingsDragging` 类、panel 的 `stopPropagation`、overlay 的 `onclick`（面板 `inset:0` 铺满，本来也没有「点外面」这回事） |

第 25 行那个「甩一下」的快捷判决（速度 > 0.3px/ms 直接按方向定案）被删掉了 —— 它会让

> ⚠️ **「速度不参与」这条已被同日下一条日志取代**：用户要的「甩一下」仍然要，只是形式必须是
> **动量投影**（`进度 + 速度 × 常量` 之后再比 0.5），而不是阈值型的方向定案 —— 详见本文件置顶那条。

## 2026-09-17 — 任务清单面板在「打开已有会话」时永远不显示

**现象**：`ChatView.tsx` 1117 行的「任务清单小面板」，mock 跑 `task` 剧本时后端 ctx 里确实写进了任务清单
（`task_list_write` → `runner.applyTaskListOp` → `ctx.taskList`，`artifacts/e2e/diag-tool-status.log` 可查），
但面板时隐时现：本轮刚跑完那一下能看到（header 计数对），**刷新页面 / 切走再回来就又没了**。

**根因（一句话）**：`taskListState` 是进程内 store，唯一写点是 `done` 事件触发的 `refreshTaskList`；
而「打开一个已存在的会话」走的是 `setActiveConversation → loadConversationCtx`，
后者只把 ctx 塞进 `appState.conversations`，**从不回填 `taskListState`**。
于是一个「历史上跑过、ctx 里有任务清单」的会话，打开后面板永远不渲染
（`parseTaskListLines(taskList()).length === 0` ⇒ `<Show>` 直接不挂）。

**修法**：`store/loadConversationCtx()` 在 `actions.setConversationCtx()` 之后补一行
`taskListActions.set(conversationId, ctx.taskList ?? '')`。
这样两条路径都能回填：`done` → `refreshTaskList`（本轮刚跑完）与 `loadConversationCtx`（打开已有会话）。
`force=true` 重拉时也会重新回填，不会漏。

**验证**：`artifacts/e2e/probe-task-panel.mjs`（DOM 级探针，4 条断言全绿）：
① 面板出现 ② 计数=2 ③ 内容含 ✅/⬜ 正确 ④ **刷新页面后点开会话，面板仍在**（修前第 ④ 条 FAIL）。

**第二步（同日追加）**：用户反馈「你的截图里没有任务清单，我自己测也看不到」——
看截图才发现，面板**默认是折叠的**，界面上只有一行「📋 任务清单（2）」+ ▸，
用户感知到的是「看不到任务清单」而不是「看不到明细」。
修法：`ChatView.tsx` 的 `taskListOpen` 由 `createSignal(false)` 改成 `createSignal(true)`，
有内容时直接展开，想折叠随时点。探针同步去掉「手动点开」步骤，断言升级为
「刷新后点开会话，默认展开且清单行=2」。

**教训**：
1. store 里凡是「按会话隔离、且只在某一个运行态事件里回填」的派生数据，
   一定要在「按需加载 ctx」的入口也回填一次 —— 否则用户打开一个老会话看到的就是空的。
2. **折叠面板默认折叠 = 用户看不到内容**：「小面板」不等于「默认收起」，

## 2026-09-17 — 提问卡计时每次归零：时间由谁来定，决定了组件会不会被重挂

**现象**：AskUserCard 右上角的「阻塞中 mm:ss」每次都从 00:00 重新数。

**两个独立的成因（必须都修，只修一个现象照旧）**：

1. **时间不是后端给的**。注释里原本写着「等待期间已阻塞多久是前端自己数出来的，不依赖后端」——组件里
   `const [elapsed, setElapsed] = createSignal(0)` + `setInterval` 自加。
   投影每收到一条 SSE 就重算一次，**组件一被换掉 state 就归零**。
2. **`<For>` 按引用判定增删**（这个 bug 在 `diffSubBlock()` 里躺了很久）：
   `o.ask === newNode.ask` 比较的是**对象引用**，而 `ask` 是每次 `fold` 就地新建的字面量，
   引用永远不等 ⇒ 每轮都判定「变了」⇒ 新对象 ⇒ AskUserCard 整块重挂。
   注意这与上面那条是**同一个根的不同表现**：Solid 的 `<For>` 不做深比较，
   任何「每次都新建的嵌套对象」都会让上层 item 变成新引用，进而把整棵子树拆了重建。

**修法（时间源统一到后端）**：

- `AgentStreamEvent` 整体带上 `StreamEventBase.timestamp`（后端 `Date.now()`）。
  由 `runner.emitStream()` **统一**盖（入参类型是 `StreamEventDraft` = 分布式 Omit），
  漏写会被类型拦下 —— `http-server.ts` 有三处绕过 runner 直发（usage 广播 / 启动失败 / runner error），只能手写。
- `runController.applyEvent()` 里所有 `Date.now()` 换成 `event.timestamp`。唯一保留
  `Date.now()` 的是「本地把提问卡标成已回答」——那是纯界面动作，后端此刻没有对应事件。
- 投影的每个块 / 子块都带 `updatedAt`（「最近更新时间」为准），diff 也纳入比较。
  工具块取 `max(结果条目时间, 提问状态条目时间)`，都没有时回落到 assistant 条目的时间。
- 界面：用户块头部 + 每个 LLM 块下方各显示一个 `HH:MM:SS`。
- 阻塞计时 = `ask.updatedAt`（后端）+ 模块级共享的 1s 心跳 `clockNow()` 现算，
  组件重挂也不丢。`sameAsk()` 改为**按值比**（callId / status / answer / updatedAt / question / options）。

**教训**：「某个展示值是界面自己算出来的」这句话要高度警惕 —— 界面上凡是「什么时候」这类信息，
来源必须是后端（否则与 ctx 里那份对不上），否则只要渲染层有重算 / 重挂，它就必然漂移。

## 2026-09-17 — 侧边栏状态标记三态化 + 「切走了还在 render」的元凶：全局 streamTick

**① 状态标记三态（用户明确要求：等客户端响应不要再统一显示成主题色）**

| 状态 | 判据 | 样子 |
|---|---|---|
| 正在产出 | `runStatus === 'running'` | 主题色常亮 |
| 等客户端响应 | `runStatus === 'waiting'` | 主题色 → 灭 → 绿 → 灭 循环闪烁（`Sidebar.module.css` 的 `marker-waiting`） |
| 跑完了没看 | `!isConversationAlive(conv) && isConversationUnread(conv.id)` | 绿色（`--success`）常亮 |

「未读」是**新增的纯前端状态**（`state.ui.unreadConversationIds`，进 localStorage）：`endRun()` 里
`convId !== activeConversationId` 时标上，`setActiveConversation()` 时清掉，删会话时一并清。
它跟运行态**正交** —— 会话还活着时不显示绿点。头部的「等待输入」chip 也跟着用 `--success`。

⚠️ 闪烁的 `animation-timing-function: steps(1, end)` 是**必须的**：不加它，颜色会在关键帧之间渐变，
效果是「呼吸」而不是「闪灯」。

**② 从一个运行中的会话切走，[dom-mutations] 还在刷 —— 设计问题，不是 Solid 的固有表现**

`renderTree` 这个 memo 里无条件读 `streamTick()`，而 tick 在 `handleStreamEvent()` 里**任何会话**的事件都 +1；
memo 又每次 `fold` 出一个**新对象**，Solid 的 `<For>` 按引用比对 ⇒ 于是「A 在跑、我在看 B」时，
A 的每个事件都会把 **B 的消息列表整棵拆了重搭**。切会话那一刻有 mutations 是正常的（内容本来就要换），
**持续刷才是 bug**。修法一行：只给 `convId === appState.activeConversationId` 的事件打拍子。
（overlay 本身是 `createStore`，切回 A 时 memo 会因 `activeConversationId` 变化重算并读到最新 overlay，
所以「只给当前会话打拍子」不会掉内容。）

**教训**：「用计数器强制刷新」的计数器一旦做成**全局**的，就退化成「任意会话的事件刷任意视图」——
它的作用域必须和它要刷新的那个视图一致。

## 2026-09-17 — 「跑完了还显示运行中 / 刷新后在跑的任务收不到消息」：两个独立的小漏

**① 状态停在 running 直到刷新** —— 根因在**序列化**，不在时序。

`GET /api/conversations` 里 `runStatus` 是「活着才下发」：`aliveIds.has(id) ? runner.runStatus() : undefined`。
run 结束后它是 `undefined`，**`JSON.stringify` 会把这个键整个丢掉** —— 于是前端 `refreshConversationMeta()`
里的 `Object.assign(conv, meta)` **压根不碰**本地那份 `'running'`（键不存在 = 不覆盖）。刷新页面之所以就好了，
是因为 `initApp()` 是 `setState('conversations', uiConvs)` 整表重建，那份脏值随对象一起被丢掉。

实证（`artifacts/e2e/probe-runstatus.mjs`，内置 mock 的 text 剧本跑一轮）：
SSE 事件流完整到 `… → agent_end → done`，而结束后列表里该会话的 meta 是
`{id, folderId, title, modeId, createdAt, updatedAt}` —— **`hasOwnProperty('runStatus') === false`**。
（顺带排除了「done 没送到」的假设：done 确实到了。）

修两处：`endRun()` 里显式 `setConversationRunStatus(convId, 'stopped')`（立即生效，不等 meta 往返）；
`refreshConversationMeta()` 里补一行 `conv.runStatus = meta.runStatus`（**可选字段必须单独赋，不能指望 Object.assign**）。

**② 刷新页面后在跑的会话收不到任何新事件** —— 订阅只在 `beginRun()` 里建，
刷新后前端一个 SSE 订阅都没有，而后端那个 runner 还在跑 ⇒ 事件无处可送。
修法：`ChatView` 里加一个 `createEffect`，凡是列表里 `runStatus` 为 running / waiting 且未订阅的会话都接回来
（`isSubscribed()` 去重）。它同时覆盖「切走再回来」这类重连场景。

**教训**：运行态这种「后端可选下发」的字段，**`Object.assign` 不是同步、是合并** —— 想清掉旧值只能显式赋值。
凡是「刷新一下就好了」的现象，先怀疑「本地那份从来没被清掉」，而不是后端没更新。

## 2026-09-15 10:35 — 「选择文件夹出错 / RPC request timed out.」：默认超时 1 秒，而人在挑目录

用户复现给出了确切的报错原文，这条线索直接把上一节留的悬念结掉了 —— **根因不在文件夹逻辑，而在 RPC 的超时**。

`src/mainview/localBridge.ts` 的 `dialogPickFolder()` 捕获到 `Error("RPC request timed out.")`，经 `alertMsgbox('选择文件夹出错', …)` 弹出。这句报错的出处是 `.hutch/devkit/api/shared/rpc.ts`：

```
:188  const DEFAULT_MAX_REQUEST_TIME = 1000;
:264  const requestMaxRequestTime = requestOptions?.maxRequestTime ?? maxRequestTime;
:278  listener?.reject(new Error("RPC request timed out."));
```

**`defineRPC` 的请求超时默认只有 1000ms**。而 `dialogOpen` 走的是**阻塞式原生目录对话框** —— 对话框一直开着等人选，人手挑目录必然超过 1 秒 ⇒ 请求端在对话框还开着的时候就已经 `reject` 了。整套「选完文件夹停在本地」的现象链条到这里才完整：先前的修复解决的是「选到了但被丢掉」，而真机上更早的一步是**请求根本就没等到对话框关闭**。

修法一行，`src/mainview/rpc.ts`：

```ts
rpc: Electroview.defineRPC<AppRPC>({
	maxRequestTime: Infinity,	// 默认 1000ms 会打断阻塞式原生对话框
	handlers: { requests: {}, messages: {} },
}),
```

SDK 对 `Infinity` 是**显式支持**的（`if (requestMaxRequestTime === Infinity || !requestListeners.has(requestId)) return;` —— 直接不注册定时器）。本项目渲染进程的 RPC 面全是**本地能力**（对话框 / shell / envInfo / 窗口），都由用户操作驱动，没有「该超时」的语义，所以整体关掉是合适的，不必逐方法配置。主进程侧 `src/bun/index.ts` 的 `BrowserView.defineRPC` **只注册 handler、不发起请求**，无需同步修改（对称性上也没有意义）。

## 2026-09-15 10:20 — 同一问题的收尾：给「够不到的那段链路」装上观测点

| 主进程日志通道 | 存在且可用：`rpc.send.log` → `windows` 侧 `messages.log` handler → `console.log`，与 `logMsg` 同一条 stdout，**dev 下即 `dev-app.log`** |

**顺手**

- 按钮文案「新建任务」→「**新建会话**」（用户要求）。`artifacts/e2e/` 里 5 个探针的 `getByRole('button', { name: '新建任务' })` 同步改名，否则回归脚本会在第一步就挂。

**教训**

1. **受控组件 ≠ 组件不会自己改自己的值**：这个 Lit 下拉框选中时会直接写自己的 `text`，而父层的受控绑定只在值变化时才覆盖回去 —— 于是「父层算出来还是同一个值」就等价于「永远不纠正」。封装受控组件时，要确认对方内部是否也写这个属性；会写的话，事件处理完必须**无条件回写一次**，不能依赖 diff。

- `probe-click-order.mjs`：点最后一个会话 → 顺序不变、tooltip 的「更新」不变。**并做了反向验证**：临时把 `updatedAt = Date.now()` 加回去，探针立刻复现（顺序翻转成 `[E2E 子Agent显示, 123]`、「更新」从 13:38:42 变成 14:26:53），改回来即转绿 —— 这样才不算假绿。

1. **前端不要伪造后端字段**：乐观更新 `updatedAt` 看起来无害，但它同时是**排序键**和**展示值**——只要有一条「读」的路径也会触发它，读操作就会改变列表语义。字段归谁所有，时间戳就该由谁给。

## 2026-09-14 10:20 — 「添加文件夹」点不动：`pickFolder` 没传 + `Folder.path` 根本没接线

用户反馈两条：① `addFolder(idOrPath, name?)` 为什么要 `name`；② 点「新建文件夹」没有任何作用，任务列表里永远只有「本地」。

**证据**：`~/.mindthegap-harness/settings.json` 与两份历史备份（`settings.json.v1bak` / `app-state.json`）里 `folders` **一直只有 `local` 一条**，37 个会话的 `folderId` 全是 `local` —— 这个功能从落地起就没成功用过。

**根因（三层，缺一不可）**

1. **选不中目录（直接原因）**：`localBridge.dialogPickFolder()` 调 `rpc.request.dialogOpen({ multiple: false })` 时**没传 `pickFolder: true`**，而 `rpc-handlers.ts` 里是 `canChooseFiles: !params?.pickFolder` → 实际拿到 `canChooseFiles: true / canChooseDirectory: true`，Windows 下弹的是**文件选择框**，选不中目录只能取消 → 永远返回 null。`pickFolder` 在 `src/` 里**没有任何调用方传过**（`as any` 把类型检查也绕过去了），是死参。
2. **`name` 是历史残留**：`git show 8316a41`（v1）起就是「两参 = id + 显示名 / 一参 = 路径」的重载，注释写着「支持两种调用」。但两个调用点（Sidebar / ChatView）**都传 name**，所以 `uid()` 分支和 `path: hasExplicitName ? idOrPath : idOrPath` 这个自等三元从来没被执行过；`name` 又恰好等于 `basename(path)`。
3. **加进来也没用（语义没接）**：`Folder.path` 在整个 `src/bun/` 里**零引用**。`runner.ts` 是 `this.runningDir = params.request.runningDir || process.cwd()`，而前端 `agentBridge.runAgent()` 的 body 里**没有 `runningDir`** —— 于是 `plugins/**/prompt.md` 里的 `{{ runningDir }}`（「运行目录」）恒为 app 自己的 cwd，用户选的目录既没进提示词、也没进文件工具的相对路径基准与 `bash` 的 cwd。

**修复**

- `Folder` 去掉 `name`：`id` 就是绝对路径，「本地」= 固定 id `'local'` 且无 `path`；显示名由 `shared/utils.ts` 新增的 `folderLabel()` 取路径最后一段现算（Sidebar 与 composer 下拉共用）。
- `addFolder(path)` 收敛成单参数 + 同路径去重 + 返回 `Folder | null`；Sidebar 拿到非 null 就展开它（新文件夹一定是空的，不展开看起来仍像「没反应」）；ChatView 在 composer 下拉里新建时顺手把当前会话切过去。
- `dialogPickFolder()` 显式传 `pickFolder: true`，并把该字段补进 `shared/rpc.ts` 的 `dialogOpen.params`（顺手去掉 `as any`）。
- **接线**：`ChatView.handleSend` 用会话所属文件夹的 `path` 作为 `AgentRunRequest.runningDir` 传下去 → 提示词 `{{ runningDir }}` + 文件工具 `resolvePath` 的基准 + `bash` 的 cwd 全部落到该目录；「本地」没 path，后端回退 `process.cwd()`。
- 顺带修一个真 bug：`store.removeFolder()` 只在前端把会话的 `folderId` 改成 `'local'`，**从不回写后端** → 重启后这些会话挂在一个已不存在的文件夹上，而侧边栏只按 `state.folders` 渲染 → 任务从列表里「凭空消失」。现在对受影响的会话逐个 `PUT /api/conversations/:id { folderId: 'local' }`。
- `tests/issues.spec.ts` 的文件夹用例选择器已全部失效（CSS Module 哈希成 `_tree-folder-name_dgzsx_363`，`.tree-folder-name` 匹配不到任何元素），改为前缀选择器 `[class^="_tree-folder_"]` + `title` 定位；且删除按钮是 `header:hover` 才 `display`，必须先 hover header 再点。

**验证**：新增一次性探针 `artifacts/e2e/probe-folders.mjs`（跑真实 vite dev server + 真实 Agent Service）—— 加文件夹 → 侧边栏只显示目录名（页面上不出现完整路径）→ 后端落盘 `id === path` 且无 `name` → 会话归到该文件夹下（自动展开）→ 同路径去重 → 删文件夹后后端同步删除 + 会话回写 `local`：**全部通过**。`npx playwright test -g "文件夹可删除"` 也已转绿。

**教训**

1. **RPC 参数不要用「反义的默认值」**：`canChooseFiles: !params?.pickFolder` 这种不传就等于选文件的设计，漏传不报错、只静默降级成一个看起来合理但不可用的对话框。给参数定默认值时先问「漏传会怎样」，并确保关键参数至少有一个真实调用点 —— `pickFolder` 从落地到这次被发现，一次都没被传过，`as any` 还让类型检查彻底失效。
2. **写进类型 ≠ 接线完成**：`Folder.path` 有类型、有持久化、有 UI 采集，却没有任何消费方。判断某字段是否真的生效，要 grep 它在**消费侧**的出现，而不是看它在数据模型里是否存在。
3. **删字段不会让老数据里的字段消失**：类型里删掉 `name` 之后，前端 `loadBackendState` 仍会把 settings.json 里那份 `name` 原样读进 store，再由 `saveBackendSettings` 原样写回 —— 于是它在后端与前端之间无限回流（本次实测就是这么回流的）。要么手工清一次老数据，要么在边界显式映射。

## 2026-09-12 02:50 — token 账本：每轮调用可见 + 中断时小计

用户反馈：「模型自主完成了多轮思考和工具调用，但最终只能看见一个总的 token 消耗，而且这个数字还不对（可能是后续消息覆盖了原本的数字），也看不见 LLM 调用了多少次」。

### 1. 两个真 bug（都不是显示层的小毛病）

**① 前端在覆盖而不是累加。**
```ts
case 'usage':
    actions.updateMessage(convId, msgId, { tokens: event.tokens });   // 每次都覆盖
```
一次用户消息期间会有 N 次 LLM 请求（多轮工具调用 + 反思 + 子 Agent），覆盖的结果就是只剩最后一次的数字 —— 这正好解释了用户说的「数字不对」。

**② 反思和工具内部 LLM 的用量根本没进账本。**
`instance.tokens` 只在 `agentLoop` 主调用之后 `mergeTokens` 一次，而 `reflect()`（反思）和 `toolSubLlm()`（web_search 的相关性打分）各自都是一次真金白银的请求，都没记。反思经常比正文还长，漏掉它账本能少一半。

### 2. 事件设计

`usage` 事件拆成两种 scope：

| scope | 何时发 | 载荷 | 前端 |
|---|---|---|---|
| `call` | 每次 LLM 请求结束 | `seq` / `round` / `purpose` / `input` / `output` / `durationMs` | 一行淡色流水 `🧮 #3 第2轮 · ↑1.3k ↓130 · 共 1.4k · 493ms` |
| `loop` | agentLoop **不再重入**时 | `loopDelta`（本段增量）/ `tokens`（实例累计）/ `loopCalls` / `reason` | 高亮小计 `∑ 本段 2 次调用 · ↑2.9k ↓290 · 本段共 3.2k · 累计 7.2k · 等待用户回答` |

关键取舍：**会重入的段不发小计**。钱还要接着花，每段都报会在界面上留下一串互相矛盾的小计。所以 `emitLoopUsage` 只在 `nextTrigger === null` 时调用。

### 3. 「等用户」还是「等子 Agent」——光看 status 分不开

两者都会把实例置成 `pending`，而且 callId 都留在 `pendingCallIds` 里：

```ts
// ask_user
instance.status = 'pending';           // 等用户点按钮
// delegate
parent.status = 'pending';             // 等子实例终态
```

第一版按 `status === 'pending' → ask_user` 判，结果委托被标成了「等待用户回答」。改用现成的 `isClientToolResult(instance, callId)` 逐个检查 pending 的 callId —— 这才是真正的区别。

### 4. 前端

- `MessageBlock` 新增 `usage` 类型；新增 `addMessageTokens` 累加 action（顺带记 `llmCalls`）。
- 只有 `scope='call'` 才计入总量：`loop` 是对已播报数据的二次汇总，重复计入会翻倍。
- 消息脚注改成 `共 N 次 LLM 调用 · tokens ↑x ↓y`。
- 数字统一走 `fmtTokens()`（1234 → 1.2k），否则四位数起步的 token 会把一行撑爆。

### 5. 验证（零 token，本地 mock）

mock 加了 `multi` 剧本（连抓两次 → 提问 → 回答后 finish），并把 usage 改成逐次递增，方便肉眼核对累加。新增 `artifacts/e2e/drive_usage.py`。

## 2026-09-11 11:38 — Agent 架构 v2 端到端验证：三个只有真跑才暴露的 bug

### 0. 验证方法：把 Agent Service 单独跑起来（不依赖 Electrobun 窗口）

### 1. 【阻塞】反思轮之后整个 run 卡死：`maybeReenter` 被 `busy` 守卫挡掉

**现象**：根实例（`intent`，`reflectionCount: 1`）在第一轮"无 tool_call"结束 → 正常发出 `reflection` 事件 → **然后就再也没有任何动静**。没有 `agent_end`、没有 `done`，实例永远停在 `running`，`waitDone()` 永不 resolve。请求日志里恰好只有 2 条（agent_loop + reflection），第 3 次请求从来没发出去。

**根因**：`endPath()` 的反思分支里直接调了 `this.maybeReenter(id, 'reflection')`，而 `endPath()` 是被 `agentLoop()` **`await`** 的——此时 `agentLoop` 的 `finally` 还没执行，`this.busy` 里仍然握着这个实例 id，`maybeReenter()` 第一道守卫 `if (this.busy.has(id)) return;` 直接把它吃掉。同理 `dispatch()` 里 `finish` 分支 `await this.endPath()` 也踩同一个坑（`finish` 后同样无法重入）。

**修复**：
- `endPath()` 的返回类型从 `Promise<void>` 改为 `Promise<LlmTrigger | null>`：走了反思轮就 `return 'reflection'`，真结束就 `return null`。
- `agentLoop()` 把「重入」从 try/finally **之后**的一条语句挪进 `finally`，紧跟 `this.busy.delete(id)` 之后：`if (nextTrigger) this.maybeReenter(id, nextTrigger)`。这样连 `return` 提前退出的路径（预算耗尽 / 无 tool_call / finish）也一定会先释放 busy 再重入。
- `dispatch()` 的 finish 分支改为 `return await this.endPath(...)`，把触发类型一路带回 `agentLoop`。

**教训**：设计稿里「执行工具即退出 agentLoop、由调度器按状态重入」这条不变式，**要求 busy 的释放先于任何重入判断**。凡是「在 agentLoop 内部 await 出来的收尾逻辑」，都不能自己调调度器——只能把意图交回给持锁者。

### 2. 【阻塞】带 tools 的请求 400：`reasoning_content` 必须"每条 assistant 都带字段"

**现象**：反思重入的那一次请求稳定 400：

```
The `reasoning_content` in the thinking mode must be passed back to the API.
```

**排查过程**（值得记，因为第一直觉是错的）：
1. 先怀疑解析漏了 —— 打印 `ctx.json`，assistant 消息的 `reasoningContent` 确实是空。
2. 写探针直接打 API：**同一轮响应里 `reasoning_content` 字段存在但值为 `''`**（模型没思考），且「带 rc / 不带 rc / rc 为空串」在**不带 tools** 时**都能通过**。
3. 决定性一步：把 harness 真实发出的 payload（`requestLog.dumpPayload: true` 会把完整请求写到 `conversations/<id>/workspace/tmp/llm/<logId>.json`）**原样回放**：
   - 原样 → 400
   - **删掉 `tools` 参数** → 通过
   - 给 assistant 补 `reasoning_content: ""` → **通过**

**结论（真实规则）**：**请求里只要带 `tools`，DeepSeek 思考模式就要求每一条 assistant 消息都"携带" `reasoning_content` 字段** —— 判定的是**字段是否出现**，不是值是否非空。空串 `''` 完全合法。

**根因**：`toOpenAiWireMessages()` 里写的是 `if (msg.role === 'assistant' && msg.toolCalls?.length)`，只有**带 tool_calls 的 assistant** 才回传 `reasoning_content`。v1 里这条路径永远不会出问题（纯文本 assistant 一出现就代表本轮结束了，不会再发第二次请求）；**v2 的反思轮让"纯文本 assistant"留在历史里继续下发**，于是第一次真正触发。

**修复**：assistant 分支无条件写出 `reasoning_content: msg.reasoningContent ?? ''`，`tool_calls` 才是可选附加。

**教训**：AGENTS.md 里「思考模型多轮工具调用必须回传 reasoning_content」这句话**不够精确**，容易实现成"只在工具调用消息上回传"。正确表述见易错点速查。

### 3. 父 Agent 提前重入：`delegate` 的 callId 被误判为"已解析"

**现象**：`intent` 委托 `explore` 后，**子 Agent 还在跑**，父实例就多跑了一轮（请求日志里出现 `trigger=tool_results`），并且把这轮回答当成最终结论汇报给用户（"委托已发出，等待其返回结果"）。等子 Agent 真正返回、父实例被唤醒后，父又推翻前面说的话重新汇报一遍。

**根因**：`dispatch()` 里循环完一批工具调用后有一步「已完成的结果从 `pendingCallIds` 里摘掉」：`filter(id => !resolved.includes(id))`，而 `resolved.push(call.id)` 是无条件对每个工具调用执行的。`delegate` / `resume_pending_child` / `resume_completed_child` 的**即时返回值只是占位**（"未完成，完成后回填到这里"），真正结果要等子实例进终态时由 `handleChildTerminal()` 写回 —— 但它们同样被塞进了 `resolved`，于是 callId 被从 `pendingCallIds` 摘掉，后面那句 `if (pendingCallIds.length > 0) return null; // 等子 Agent，不重入` 就失效了。

**修复**：这三个编排原语的返回值都带 `structured.status === 'pending'` 标记，用它判延迟：

```ts
// （deferred 的调用故意不进 resolved，让它留在 pendingCallIds 里等子实例终态）
if (result.structured?.status !== 'pending') resolved.push(call.id);
```

**验证**：修复后请求日志里父实例在委托之后的下一次请求 `trigger=delegate_return`（不再出现 `tool_results`），说明它老老实实等到了子实例终态。

### 4. 顺带修掉的小问题

- **根实例的 user 消息重复**：`createInstance()` 已经把 task 作为首条 message 放进去了，`run()` 又 push 了一次 `userMessage`（落盘可见两条一模一样的 user 消息，白白多花 token）。改为只在「唤醒已有实例」时补 push。

- **请求日志的 `purpose` 被污染**：反思重入的那一轮是**带 10 个工具的正常轮次**，却被记成 `purpose: 'reflection'`（`purpose: trigger === 'reflection' ? ...`），把「反思轮」和「反思后重入的正常轮」混成一类，用量统计看不出真实开销。改为 `agentLoop` 里恒 `purpose: 'agent_loop'`，靠 `trigger: 'reflection'` 区分；真正的反思请求（无工具）仍由 `reflect()` 发 `purpose: 'reflection'`。

## 2026-09-10 13:20 — 无边框窗口丢阴影/圆角/snap 排查 + 启动加载页 + FFBox-UI 注入验证

用户反馈三点：(1) 无边框窗口能拖但没阴影、没圆角、Windows snap 不触发；(2) hutch 偶发白屏，希望 index.html 有加载页；(3) FFBox-UI 若在 index.html 注入会不会重复引入。

### 1. 根因：`titleBarStyle: 'hidden'` 在 Windows 上建成了 WS_POPUP

**排查手段**：不猜，直接把运行中窗口的样式位读出来。用 Python ctypes 调 `GetWindowLongPtrW(hwnd, GWL_STYLE)`（PowerShell 的 `Add-Type` 被本机安全策略拦截，改用 ctypes 可行）。

```
titleBarStyle: 'hidden'  →  GWL_STYLE = 0x94000000
                            只有 WS_POPUP | WS_VISIBLE | WS_CLIPSIBLINGS
                            WS_CAPTION / WS_THICKFRAME / WS_SYSMENU / MINBOX / MAXBOX 全无
```

`WS_CAPTION` + `WS_THICKFRAME` 缺失 → 无 DWM 投影、无 Win11 圆角、不能拖边缘缩放；`WS_MAXIMIZEBOX` 缺失 → Win11 snap layouts（悬停最大化按钮弹出的分屏面板）不出现。与 Electron 生态里 `frame:false` 的经典症状完全一致（Electron 的 `thickFrame` 就是控制 `WS_THICKFRAME`）。

### 2. 试错过程（每次实验都读一次样式位）

| 方案 | GWL_STYLE | 客户区上偏移 | 结论 |
|---|---|---|---|
| `hidden` + 什么都不补 | `0x94000000` | 0 | 有自绘标题栏，但无投影/圆角/snap |
| `hidden` + 运行时补 `CAPTION+THICKFRAME+SYSMENU+MIN+MAX` | `0x94CF0000` | **29px** | 投影回来了，但原生标题栏占掉顶部 29px → 变成「原生标题栏 + 自绘标题栏」两条，不可用 |
| `hidden` + 只补 `THICKFRAME+SYSMENU+MIN+MAX`（不含 CAPTION） | `0x940F0000` | 6px | 客户区没被标题栏吃掉，可行 —— 等价 Electron `frame:false` + `thickFrame:true` |
| **`hiddenInset`**（electrobun 自带） | `0x16C40000` | **0** | 有 `WS_CAPTION+WS_THICKFRAME`，投影/圆角/缩放都在，且客户区上偏移 0 |
| `hiddenInset` + 补 `SYSMENU+MIN+MAX` | **`0x16CF0000`** | **0** | 最终方案，全部达标 |

关键发现：electrobun 的 `hiddenInset` 走的是 `Titled:true + FullSizeContentView:true`，并且**在 Windows 侧正确处理了 `WM_NCCALCSIZE`**，所以有 `WS_CAPTION` 的同时原生标题栏不占顶部空间 —— 这比自己去补样式位干净得多。

另外试了 `styleMask: { FullScreen: true, ... }` 想补出 `WS_MAXIMIZEBOX`，**无效**（样式位没变），说明 `styleMask` 在 Windows 侧只映射了很少几个字段。

### 3. 落地

- `src/bun/win32.ts`（新增）：`patchFramelessWindowFrame()`，用 `bun:ffi` dlopen `user32.dll`，`FindWindowA` 定位窗口 → `GetWindowLongPtrW` 读 → `SetWindowLongPtrW` 补 → `SetWindowPos(SWP_FRAMECHANGED)` 让 DWM 重算非客户区。全程 try/catch 静默降级，非 win32 直接返回。
- `src/bun/index.ts`：`titleBarStyle: 'hiddenInset'`，创建窗口后调 `patchFramelessWindowFrame('MindTheGap-Harness')`。实测日志 `[win32] 窗口样式补丁已应用: 0x16c40000 -> 0x16cf0000`。

### 5. FFBox-UI 在 index.html 注入 —— 不会重复，但也没必要

做了对照实验：一次带 `<script src="../../vendor/ffbox-ui/dist/esm/ffbox-ui-autoregister.js">` 构建，一次不带。

### 易错点 / 经验

- **Cottontail 不用 Bun.file / Bun.pathToFileURL**：和项目历史一致，spawn 走 `node:child_process`。
- **Cottontail 的 fetch ReadableStream 不工作**（沿用 `model.ts` 已有注释），所以 HTTP MCP 强制走单 JSON 响应。
- **`-stream tools/list_changed` 等服务器通知是消息而非响应**：不能分配 pending id（id 为 undefined），`handleMessage` 里要把"有 method 无 id"和"有 method 有 id"区分开，前者不回任何东西，后者回 method not found。
- **Cottontail `child_process.spawn('npx')` 在 Windows 上会 ENOENT**：npx/npm/yarn/pnpm/bun/deno 这些是 .cmd 批处理，在 `resolveCommand` 里自动补后缀。**用户填 `node` 直接可用**，因为 node.exe 是真二进制。
- **stdin 协议通道 vs 调试日志**：MCP 子进程**绝对不能用 `console.log`** 往 stdout 写日志，必须走 console.error（stderr）。stdio 客户端的 stdout 是协议通道，任何多余字节都会让 JSON.parse 报错然后被静默忽略，调试极痛苦。
- **工具名限制**：DeepSeek/OpenAI 都要求 `^[a-zA-Z0-9_-]+$`。中文名（如"正弦计算器"）做前缀会全被替换成下划线，最终 trim 成空字符串——所以默认内置示例名是 `sine 正弦函数（内置示例）`，sanitize 后得到 `sine`。在 UI 描述里强调"建议以英文起头"。
- **保存设置后立即生效**：UI 上"保存/启停"按钮在 debounce（500ms）之前用户可能就关掉面板，所以 MCP 操作走 `flushMcpServers()` 立即 PUT，PUT 接口内部调 `mcpManager.syncAll()`（内部串行化锁）。
- **`settings.json` 字段向后兼容**：老用户的 settings.json 没有 mcpServers 字段，直接 `...raw` 会被 raw 里不存在的 undefined 覆盖默认值。`getSettings` 改成"逐项只覆盖 raw 里确实存在的 key"。

### 1. engine.ts 字段引用错误 → runAgent crash

- **现象**：前端收到模型回复时，整段文字（block）输出后才能看到，而非逐字/逐句流式显示。

### 3. 对话消息未持久化 → 重启后历史记录丢失

- **现象**：正常聊天后重启应用，从任务列表选原来的对话，看不到任何记录。

- **教训**：前后端状态分离后，必须显式设计"前端状态何时回写后端"的时机。流式传输完成（finishStreaming）是自然回写点。

### 4. Settings 页输入字符即失焦

- **现象**：在模型设置页的输入框中输入一个字符，输入框立即失焦，需重新点击才能继续输入。
- **根因**：每次 `oninput` 触发后调用 `props.onChange`，该回调创建全新的 provider 对象（深拷贝 + 修改），导致 `ProviderEditor` 整体重渲染。`<For>` 组件检测到 `models` 数组引用变化，销毁并重建所有子 DOM，输入框被销毁重建自然失焦。
- **修复**：使用 `createStore` 管理本地可变编辑状态（`const [local, setLocal] = createStore({ provider: deepClone(props.provider) })`），输入时直接 `setLocal("provider", "models", mIdx, "id", value)` 就地修改 proxy 属性，不触发整体重渲染。仅在 `handleSave` 时通过 `props.onChange(local.provider)` 一次性提交。
- **教训**：Solid.js `<For>` 对数组引用变化极度敏感——引用变了就销毁重建所有子 DOM。内联编辑场景必须用 `createStore` 本地状态就地修改，不能每次输入都创建新对象。

### 5. deleteConversation 后列表不更新

- **现象**：点击 Sidebar 删除按钮后，conversation 从后端删除成功，但前端列表不刷新。
- **根因**：`deleteConversation` 中使用 `setState('conversations', produce((list) => list.filter((c) => c.id !== id)))`。Solid.js 的 `produce` 包装的是可变 proxy，`filter()` 返回新数组但不会修改原始 proxy，导致 UI 不更新。
- **修复**：改为 `setState('conversations', (prev) => prev.filter((c) => c.id !== id))`，函数式 setState 直接返回新数组替换旧值。
- **教训**：`produce` 适合就地深改（push、splice、属性赋值），不适合返回新数组替换顶层。替换整个数组必须用函数式 setState。

## 2026-09-01 晚 — 模型配置错误 & UI 下拉菜单 & DevTools

## 2026-09-01 — RPC 打通 & Agent 引擎落地

- 主进程向渲染进程推消息需要在窗口创建后等 webview 就绪。`index.ts` 里 setupWebviewBridge() 用 500ms 轮询等 `win.webview.rpc.send.agentStream` 可用。

- `defineRPC` 需要泛型参数 `<AppRPC>` 才完整类型检查。

## 2026-09-01 — Cottontail 运行时注意事项

- `process.cwd()` 和 Bun 环境可能不同，agent engine 里 resolvePath 时要注意。

- `Bun.resolveSync` / `Bun.pathToFileURL` 在 Cottontail 下不可用，要换成 `node:path` 的 `resolve()`。

- `Bun.spawnSync` 在 Cottontail 下可用（因为 node:child\_process 兼容层），但参数可能需要适配。

- fetch 在 Cottontail 下可用，支持 ReadableStream。

## 2026-09-01 深夜+ — 三大问题根治（Sidebar 响应式 + removeFolder produce 坑）

1. **侧边栏会话不显示**（"新对话不往左侧加"）根因：`<For each={convs}>` 的 `convs` 是每次 render 返回的新数组（普通函数），Solid 不把普通函数返回值当响应式源，store 变化后 `<For>` 不重渲染。修复：把按文件夹过滤+排序逻辑包进 `createMemo`（`conversationsInFolder(folderId)` 返回 memo），JSX 用 `convs()`。**教训：Solid 的** **`<For>`/`<Show>`** **的 each/when 必须是 signal 或 memo，不能用普通函数调用结果**
2. **文件夹删除按钮点击无效** 根因：`removeFolder` 里用 `produce((list) => list.filter(...))`，solid-js/store 的 `produce` 对"返回新数组替换顶层"的写法不生效（递归代理不提交顶层替换）。修复：改成函数式 `setState("folders", (prev) => prev.filter(...))`。**教训：需要替换整个数组时用** **`(prev) => ...`** **函数式 setState，produce 只适合就地深改**
3. **AI 回复空白** 端到端验证：浏览器 transport=http 下发送消息 → SSE 流式事件 `agent_start→text→usage→agent_end→done` 完整到达，assistant 消息完整渲染；reload 后消息从 localStorage 持久化恢复也正常。当前代码在干净浏览器环境不再空白
4. 新增 `tests/issues.spec.ts` 三大问题回归测试（会话进侧边栏 / 文件夹删除按钮 / AI 回复非空），**5 个测试全绿**（`npx playwright test`）

## 2026-08-31 — 框架选型 & 脚手架

- electrobun 2.0 的运行时已从 Bun 换成了 Cottontail（自研 JSC 运行时 + Zig）。electrobun.config.ts 中 `build.mainProcess: "cottontail"`。所以 `Bun.file()` 等 API **不可用**，要用 `node:fs`。

- electrobun 1.x 用 `BrowserView.defineElectrobunRPC`，2.0 改成了 `BrowserView.defineRPC`。

- Electron 的 `ipcMain.handle()` 在 electrobun 中对应 `BrowserWindow.defineRPC({ handlers: { requests: { ... } } })`。

- electronbun devkit 源码在 `.hutch/devkit/api/`，遇到 API 疑问直接看这里。

- 配置文件中 `electrobun.config.ts` 用 `build.copy` 把 Vite 产物拷到 views 目录下：`"dist/index.html": "views/mainview/index.html"`。

- HMR 模式需要先起 vite dev server 再起 hutch，比较麻烦。开发阶段用 `hutch run dev` 更稳定。

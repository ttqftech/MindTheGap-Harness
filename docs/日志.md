## 2026-09-17 — 侧边栏状态标记三态化 + 「切走了还在 render」的元凶：全局 streamTick

**① 状态标记三态（用户明确要求：等客户端响应不要再统一显示成主题色）**

| 状态 | 判据 | 样子 |
|---|---|---|
| 正在产出 | `runStatus === 'running'` | 主题色常亮 |
| 等客户端响应 | `runStatus === 'waiting'` | 主题色 → 灭 → 绿 → 灭 循环闪烁（`Sidebar.module.css` 的 `marker-waiting`） |
| 跑完了没看 | `!isConversationAlive(conv) && isConversationUnread(conv.id)` | 绿色（`--success`）常亮 |

「未读」是**新增的纯前端状态**（`state.ui.unreadConversationIds`，进 localStorage）：`endRun()` 里
`convId !== activeConversationId` 时标上，`setActiveConversation()` 时清掉，删会话时一并清。
它跟运行态**正交** —— 会话还活着时不显示绿点。头部的「等待输入」chip 也跟着用 `--success`。

⚠️ 闪烁的 `animation-timing-function: steps(1, end)` 是**必须的**：不加它，颜色会在关键帧之间渐变，
效果是「呼吸」而不是「闪灯」。

**② 从一个运行中的会话切走，[dom-mutations] 还在刷 —— 设计问题，不是 Solid 的固有表现**

`renderTree` 这个 memo 里无条件读 `streamTick()`，而 tick 在 `handleStreamEvent()` 里**任何会话**的事件都 +1；
memo 又每次 `fold` 出一个**新对象**，Solid 的 `<For>` 按引用比对 ⇒ 于是「A 在跑、我在看 B」时，
A 的每个事件都会把 **B 的消息列表整棵拆了重搭**。切会话那一刻有 mutations 是正常的（内容本来就要换），
**持续刷才是 bug**。修法一行：只给 `convId === appState.activeConversationId` 的事件打拍子。
（overlay 本身是 `createStore`，切回 A 时 memo 会因 `activeConversationId` 变化重算并读到最新 overlay，
所以「只给当前会话打拍子」不会掉内容。）

**教训**：「用计数器强制刷新」的计数器一旦做成**全局**的，就退化成「任意会话的事件刷任意视图」——
它的作用域必须和它要刷新的那个视图一致。

## 2026-09-17 — 「跑完了还显示运行中 / 刷新后在跑的任务收不到消息」：两个独立的小漏

**① 状态停在 running 直到刷新** —— 根因在**序列化**，不在时序。

`GET /api/conversations` 里 `runStatus` 是「活着才下发」：`aliveIds.has(id) ? runner.runStatus() : undefined`。
run 结束后它是 `undefined`，**`JSON.stringify` 会把这个键整个丢掉** —— 于是前端 `refreshConversationMeta()`
里的 `Object.assign(conv, meta)` **压根不碰**本地那份 `'running'`（键不存在 = 不覆盖）。刷新页面之所以就好了，
是因为 `initApp()` 是 `setState('conversations', uiConvs)` 整表重建，那份脏值随对象一起被丢掉。

实证（`artifacts/e2e/probe-runstatus.mjs`，内置 mock 的 text 剧本跑一轮）：
SSE 事件流完整到 `… → agent_end → done`，而结束后列表里该会话的 meta 是
`{id, folderId, title, modeId, createdAt, updatedAt}` —— **`hasOwnProperty('runStatus') === false`**。
（顺带排除了「done 没送到」的假设：done 确实到了。）

修两处：`endRun()` 里显式 `setConversationRunStatus(convId, 'stopped')`（立即生效，不等 meta 往返）；
`refreshConversationMeta()` 里补一行 `conv.runStatus = meta.runStatus`（**可选字段必须单独赋，不能指望 Object.assign**）。

**② 刷新页面后在跑的会话收不到任何新事件** —— 订阅只在 `beginRun()` 里建，
刷新后前端一个 SSE 订阅都没有，而后端那个 runner 还在跑 ⇒ 事件无处可送。
修法：`ChatView` 里加一个 `createEffect`，凡是列表里 `runStatus` 为 running / waiting 且未订阅的会话都接回来
（`isSubscribed()` 去重）。它同时覆盖「切走再回来」这类重连场景。

**教训**：运行态这种「后端可选下发」的字段，**`Object.assign` 不是同步、是合并** —— 想清掉旧值只能显式赋值。
凡是「刷新一下就好了」的现象，先怀疑「本地那份从来没被清掉」，而不是后端没更新。

**现象**（用户报告）：在 composer 的「运行文件夹」下拉里选「+ 添加文件夹…」、并在目录对话框里选好目录之后，下拉框里的文本**仍然是 `__new__`**（那是菜单项的 `value`，不是标签）。文件夹本身加进去了、侧边栏也出现了。

- **`<ffbox-dropdown-input>` 选中一项后会把自己内部的 text 设成该菜单项的 `value`** —— 组件源码 `onSelect` 里就一句 `this.text = value`（`vendor/ffbox-ui/dist/esm/components/dropdown-input/ffbox-dropdown-input.js`）。而菜单项的 `value` 是给 `onchange` 用的标识（文件夹那条是哨兵 `__new__`、模式那条是 modeId），**根本不是给人看的标签**。
- 它在我们这里是**受控**的（`prop:text={currentFolderDisplay()}`），而 Solid 只在表达式的**值发生变化**时才写回。于是只要 `onchange` 处理完没有改变「应该显示的值」，控件就永远停在那个原始 value：

| 路径 | 显示值有没有变 | 结果 |
|---|---|---|
| 无激活会话时选「+ 添加文件夹…」 | `currentFolderDisplay()` 前后都是「选择文件夹...」 | ❌ 卡在 `__new__` |
| 目录对话框被取消 | 不变 | ❌ 卡在 `__new__` |
| 选到已存在的文件夹（`addFolder()` 返回 null） | 不变 | ❌ 卡在 `__new__` |
| 重新选中当前已选中的模式 / 剧本 | 不变 | ❌ 卡在原始 id |
| 有激活会话、真的换了文件夹 | 「本地」→ 新目录名 | ✅（所以以前看着「基本正常」） |

**修复**：三个受控下拉框（文件夹 / 模式 / 剧本）各拿一个 `ref`，`onchange` 处理完**显式把状态里的显示文本写回去**一次（`resyncDropdownText()`）—— 与已有的 `modelInputRef.text = currentModelDisplay()` 是同一套做法。关键是它在**异步分支（目录对话框）与失败分支上也要调用**，否则那些路径依旧卡住。

**顺手**

- 按钮文案「新建任务」→「**新建会话**」（用户要求）。`artifacts/e2e/` 里 5 个探针的 `getByRole('button', { name: '新建任务' })` 同步改名，否则回归脚本会在第一步就挂。
- `ChatView.renderTree` 补了 overlay 的**会话归属校验**：`overlay.conversationId !== activeConversationId` 时不再拿它去合成渲染树。此前「上一轮还在跑的时候点了新建会话」会把上一个会话的在飞内容搬进新会话，看起来就像「没切过去、还停在原来那条会话上」。

**验证**：`probe-new-conversation.mjs` 场景 B（刷新到无激活会话 → 选「+ 添加文件夹…」）：修复前 `点完后立刻 = "__new__"`、`点完后 2.5s = "__new__"`；修复后两处都是「选择文件夹...」，同时后端 folders 正确多了那条路径。`tsc -b` 全绿。（场景 A「选中一条有内容的会话 → 点新建会话」修复前后都正常：主区回到空列表、激活项变成新会话。）

**教训**

1. **受控组件 ≠ 组件不会自己改自己的值**：这个 Lit 下拉框选中时会直接写自己的 `text`，而父层的受控绑定只在值变化时才覆盖回去 —— 于是「父层算出来还是同一个值」就等价于「永远不纠正」。封装受控组件时，要确认对方内部是否也写这个属性；会写的话，事件处理完必须**无条件回写一次**，不能依赖 diff。
2. **`value` 与 `label` 不能混用**：控件拿 `value`（标识）当显示文本，一旦标识是哨兵串（`__new__`）就字面显示出来。给控件喂 `value` 做展示是设计缺陷，但发现后最省事的修法仍是「事件后回写真实显示值」。
3. **复现要贴用户的真实前提**：第一版探针从「刚加载、无激活会话」开始，两条都正常；而用户看到的两条 bug 都只在「无激活会话 / 有激活会话」这一维上分叉。写探针前先想清楚「用户当时处于哪个状态」，别只照着动作序列抄。

7. **DOM 判据别用 class 名反推状态**：`_agent-tool-preview_` 在「输出预览」和「执行中…」两个分支都会渲染，拿它判「运行中」会把成功的工具也算成运行中。读 `innerText` 的 `执行中…` / `✓` / `✗`。

## 2026-09-12 02:50 — token 账本：每轮调用可见 + 中断时小计

用户反馈：「模型自主完成了多轮思考和工具调用，但最终只能看见一个总的 token 消耗，而且这个数字还不对（可能是后续消息覆盖了原本的数字），也看不见 LLM 调用了多少次」。

### 1. 两个真 bug（都不是显示层的小毛病）

**① 前端在覆盖而不是累加。**
```ts
case 'usage':
    actions.updateMessage(convId, msgId, { tokens: event.tokens });   // 每次都覆盖
```
一次用户消息期间会有 N 次 LLM 请求（多轮工具调用 + 反思 + 子 Agent），覆盖的结果就是只剩最后一次的数字 —— 这正好解释了用户说的「数字不对」。

**② 反思和工具内部 LLM 的用量根本没进账本。**
`instance.tokens` 只在 `agentLoop` 主调用之后 `mergeTokens` 一次，而 `reflect()`（反思）和 `toolSubLlm()`（web_search 的相关性打分）各自都是一次真金白银的请求，都没记。反思经常比正文还长，漏掉它账本能少一半。

### 2. 事件设计

`usage` 事件拆成两种 scope：

| scope | 何时发 | 载荷 | 前端 |
|---|---|---|---|
| `call` | 每次 LLM 请求结束 | `seq` / `round` / `purpose` / `input` / `output` / `durationMs` | 一行淡色流水 `🧮 #3 第2轮 · ↑1.3k ↓130 · 共 1.4k · 493ms` |
| `loop` | agentLoop **不再重入**时 | `loopDelta`（本段增量）/ `tokens`（实例累计）/ `loopCalls` / `reason` | 高亮小计 `∑ 本段 2 次调用 · ↑2.9k ↓290 · 本段共 3.2k · 累计 7.2k · 等待用户回答` |

关键取舍：**会重入的段不发小计**。钱还要接着花，每段都报会在界面上留下一串互相矛盾的小计。所以 `emitLoopUsage` 只在 `nextTrigger === null` 时调用。

## 2026-09-11 11:38 — Agent 架构 v2 端到端验证：三个只有真跑才暴露的 bug

v2 重构（插件 → 模式 → 子 Agent 三层动态装载）代码写完之后，`tsc` 干净、前端 `vite build` 干净，但**一跑真模型就连环出问题**。本文记录三个必须靠端到端才能发现的 bug，以及一套「脱开 Electrobun 跑 Agent Service」的验证方法。

### 0. 验证方法：把 Agent Service 单独跑起来（不依赖 Electrobun 窗口）

Agent Service 本来就能脱离 electrobun 独立跑（`http-server.ts` 头部注释），但它是 .ts + 无扩展名 import，Node 不能直接执行。用 vite 打成一个 ESM 单文件即可：

```bash
npx vite build --config artifacts/e2e/vite.server.config.ts   # → artifacts/e2e/build/server.mjs
node artifacts/e2e/build/server.mjs                            # 监听 18999
```

配置见 `artifacts/e2e/vite.server.config.ts`（`build.lib` 单入口 + `target: node22` + `external: [/^node:/]`），入口 `artifacts/e2e/server-entry.ts` 只复刻 `src/bun/index.ts` 的「非窗口」启动顺序：`await loadSettings()` → `startHttpServer()` → `mcpManager.syncAll()`。**`loadSettings()` 必须自己先 await**——`startHttpServer()` 内部的 `reloadPlugins()` / `setRequestLogOptions()` 都依赖设置已经在内存里（index.ts 里也是这个顺序）。

驱动脚本 `artifacts/e2e/drive.py`：**先开 SSE 再发 run**（runner 只广播给当前订阅者，晚连会丢事件），全程记录事件、最后把 `ctx.json` 的实例树打出来核对。

> 这套脚本是排查用的，放在 `artifacts/`（已 gitignore），不入库。

### 1. 【阻塞】反思轮之后整个 run 卡死：`maybeReenter` 被 `busy` 守卫挡掉

**现象**：根实例（`intent`，`reflectionCount: 1`）在第一轮"无 tool_call"结束 → 正常发出 `reflection` 事件 → **然后就再也没有任何动静**。没有 `agent_end`、没有 `done`，实例永远停在 `running`，`waitDone()` 永不 resolve。请求日志里恰好只有 2 条（agent_loop + reflection），第 3 次请求从来没发出去。

**根因**：`endPath()` 的反思分支里直接调了 `this.maybeReenter(id, 'reflection')`，而 `endPath()` 是被 `agentLoop()` **`await`** 的——此时 `agentLoop` 的 `finally` 还没执行，`this.busy` 里仍然握着这个实例 id，`maybeReenter()` 第一道守卫 `if (this.busy.has(id)) return;` 直接把它吃掉。同理 `dispatch()` 里 `finish` 分支 `await this.endPath()` 也踩同一个坑（`finish` 后同样无法重入）。

**修复**：
- `endPath()` 的返回类型从 `Promise<void>` 改为 `Promise<LlmTrigger | null>`：走了反思轮就 `return 'reflection'`，真结束就 `return null`。
- `agentLoop()` 把「重入」从 try/finally **之后**的一条语句挪进 `finally`，紧跟 `this.busy.delete(id)` 之后：`if (nextTrigger) this.maybeReenter(id, nextTrigger)`。这样连 `return` 提前退出的路径（预算耗尽 / 无 tool_call / finish）也一定会先释放 busy 再重入。
- `dispatch()` 的 finish 分支改为 `return await this.endPath(...)`，把触发类型一路带回 `agentLoop`。

**教训**：设计稿里「执行工具即退出 agentLoop、由调度器按状态重入」这条不变式，**要求 busy 的释放先于任何重入判断**。凡是「在 agentLoop 内部 await 出来的收尾逻辑」，都不能自己调调度器——只能把意图交回给持锁者。

### 2. 【阻塞】带 tools 的请求 400：`reasoning_content` 必须"每条 assistant 都带字段"

**现象**：反思重入的那一次请求稳定 400：

```
The `reasoning_content` in the thinking mode must be passed back to the API.
```

**排查过程**（值得记，因为第一直觉是错的）：
1. 先怀疑解析漏了 —— 打印 `ctx.json`，assistant 消息的 `reasoningContent` 确实是空。
2. 写探针直接打 API：**同一轮响应里 `reasoning_content` 字段存在但值为 `''`**（模型没思考），且「带 rc / 不带 rc / rc 为空串」在**不带 tools** 时**都能通过**。
3. 决定性一步：把 harness 真实发出的 payload（`requestLog.dumpPayload: true` 会把完整请求写到 `conversations/<id>/workspace/tmp/llm/<logId>.json`）**原样回放**：
   - 原样 → 400
   - **删掉 `tools` 参数** → 通过
   - 给 assistant 补 `reasoning_content: ""` → **通过**

**结论（真实规则）**：**请求里只要带 `tools`，DeepSeek 思考模式就要求每一条 assistant 消息都"携带" `reasoning_content` 字段** —— 判定的是**字段是否出现**，不是值是否非空。空串 `''` 完全合法。

**根因**：`toOpenAiWireMessages()` 里写的是 `if (msg.role === 'assistant' && msg.toolCalls?.length)`，只有**带 tool_calls 的 assistant** 才回传 `reasoning_content`。v1 里这条路径永远不会出问题（纯文本 assistant 一出现就代表本轮结束了，不会再发第二次请求）；**v2 的反思轮让"纯文本 assistant"留在历史里继续下发**，于是第一次真正触发。

**修复**：assistant 分支无条件写出 `reasoning_content: msg.reasoningContent ?? ''`，`tool_calls` 才是可选附加。

**教训**：AGENTS.md 里「思考模型多轮工具调用必须回传 reasoning_content」这句话**不够精确**，容易实现成"只在工具调用消息上回传"。正确表述见易错点速查。

### 3. 父 Agent 提前重入：`delegate` 的 callId 被误判为"已解析"

**现象**：`intent` 委托 `explore` 后，**子 Agent 还在跑**，父实例就多跑了一轮（请求日志里出现 `trigger=tool_results`），并且把这轮回答当成最终结论汇报给用户（"委托已发出，等待其返回结果"）。等子 Agent 真正返回、父实例被唤醒后，父又推翻前面说的话重新汇报一遍。

**根因**：`dispatch()` 里循环完一批工具调用后有一步「已完成的结果从 `pendingCallIds` 里摘掉」：`filter(id => !resolved.includes(id))`，而 `resolved.push(call.id)` 是无条件对每个工具调用执行的。`delegate` / `resume_pending_child` / `resume_completed_child` 的**即时返回值只是占位**（"未完成，完成后回填到这里"），真正结果要等子实例进终态时由 `handleChildTerminal()` 写回 —— 但它们同样被塞进了 `resolved`，于是 callId 被从 `pendingCallIds` 摘掉，后面那句 `if (pendingCallIds.length > 0) return null; // 等子 Agent，不重入` 就失效了。

**修复**：这三个编排原语的返回值都带 `structured.status === 'pending'` 标记，用它判延迟：

```ts
// （deferred 的调用故意不进 resolved，让它留在 pendingCallIds 里等子实例终态）
if (result.structured?.status !== 'pending') resolved.push(call.id);
```

**验证**：修复后请求日志里父实例在委托之后的下一次请求 `trigger=delegate_return`（不再出现 `tool_results`），说明它老老实实等到了子实例终态。

### 4. 顺带修掉的小问题

## 2026-09-10 13:20 — 无边框窗口丢阴影/圆角/snap 排查 + 启动加载页 + FFBox-UI 注入验证

### 1. 根因：`titleBarStyle: 'hidden'` 在 Windows 上建成了 WS_POPUP

**排查手段**：不猜，直接把运行中窗口的样式位读出来。用 Python ctypes 调 `GetWindowLongPtrW(hwnd, GWL_STYLE)`（PowerShell 的 `Add-Type` 被本机安全策略拦截，改用 ctypes 可行）。

```
titleBarStyle: 'hidden'  →  GWL_STYLE = 0x94000000
                            只有 WS_POPUP | WS_VISIBLE | WS_CLIPSIBLINGS
                            WS_CAPTION / WS_THICKFRAME / WS_SYSMENU / MINBOX / MAXBOX 全无
```

`WS_CAPTION` + `WS_THICKFRAME` 缺失 → 无 DWM 投影、无 Win11 圆角、不能拖边缘缩放；`WS_MAXIMIZEBOX` 缺失 → Win11 snap layouts（悬停最大化按钮弹出的分屏面板）不出现。与 Electron 生态里 `frame:false` 的经典症状完全一致（Electron 的 `thickFrame` 就是控制 `WS_THICKFRAME`）。

### 2. 试错过程（每次实验都读一次样式位）

| 方案 | GWL_STYLE | 客户区上偏移 | 结论 |
|---|---|---|---|
| `hidden` + 什么都不补 | `0x94000000` | 0 | 有自绘标题栏，但无投影/圆角/snap |
| `hidden` + 运行时补 `CAPTION+THICKFRAME+SYSMENU+MIN+MAX` | `0x94CF0000` | **29px** | 投影回来了，但原生标题栏占掉顶部 29px → 变成「原生标题栏 + 自绘标题栏」两条，不可用 |
| `hidden` + 只补 `THICKFRAME+SYSMENU+MIN+MAX`（不含 CAPTION） | `0x940F0000` | 6px | 客户区没被标题栏吃掉，可行 —— 等价 Electron `frame:false` + `thickFrame:true` |
| **`hiddenInset`**（electrobun 自带） | `0x16C40000` | **0** | 有 `WS_CAPTION+WS_THICKFRAME`，投影/圆角/缩放都在，且客户区上偏移 0 |
| `hiddenInset` + 补 `SYSMENU+MIN+MAX` | **`0x16CF0000`** | **0** | 最终方案，全部达标 |

关键发现：electrobun 的 `hiddenInset` 走的是 `Titled:true + FullSizeContentView:true`，并且**在 Windows 侧正确处理了 `WM_NCCALCSIZE`**，所以有 `WS_CAPTION` 的同时原生标题栏不占顶部空间 —— 这比自己去补样式位干净得多。

另外试了 `styleMask: { FullScreen: true, ... }` 想补出 `WS_MAXIMIZEBOX`，**无效**（样式位没变），说明 `styleMask` 在 Windows 侧只映射了很少几个字段。

### 易错点 / 经验

- **Cottontail 不用 Bun.file / Bun.pathToFileURL**：和项目历史一致，spawn 走 `node:child_process`。
- **Cottontail 的 fetch ReadableStream 不工作**（沿用 `model.ts` 已有注释），所以 HTTP MCP 强制走单 JSON 响应。
- **`-stream tools/list_changed` 等服务器通知是消息而非响应**：不能分配 pending id（id 为 undefined），`handleMessage` 里要把"有 method 无 id"和"有 method 有 id"区分开，前者不回任何东西，后者回 method not found。
- **Cottontail `child_process.spawn('npx')` 在 Windows 上会 ENOENT**：npx/npm/yarn/pnpm/bun/deno 这些是 .cmd 批处理，在 `resolveCommand` 里自动补后缀。**用户填 `node` 直接可用**，因为 node.exe 是真二进制。
- **stdin 协议通道 vs 调试日志**：MCP 子进程**绝对不能用 `console.log`** 往 stdout 写日志，必须走 console.error（stderr）。stdio 客户端的 stdout 是协议通道，任何多余字节都会让 JSON.parse 报错然后被静默忽略，调试极痛苦。
- **工具名限制**：DeepSeek/OpenAI 都要求 `^[a-zA-Z0-9_-]+$`。中文名（如"正弦计算器"）做前缀会全被替换成下划线，最终 trim 成空字符串——所以默认内置示例名是 `sine 正弦函数（内置示例）`，sanitize 后得到 `sine`。在 UI 描述里强调"建议以英文起头"。

### 2. 流式输出未启用 → 整段文字一次性返回

- **现象**：前端收到模型回复时，整段文字（block）输出后才能看到，而非逐字/逐句流式显示。
- **根因**：`streamOpenAiChat` 函数中 `stream` 设置为 `false`，导致整个响应一次性返回，而非 SSE 流式。同时未使用 `parseSseStream` 处理流式响应。

### 3. 对话消息未持久化 → 重启后历史记录丢失

- **现象**：正常聊天后重启应用，从任务列表选原来的对话，看不到任何记录。
- **根因**：对话消息只存在于前端内存（solid-js store），后端 `storage.ts` 创建的 JSON 文件 `messages` 为空数组。`engine.ts` 运行后不会将消息写入存储，前端也没有回写逻辑。重启后从后端加载的对话自然无消息。
- **修复**：
  1. `storage.ts` 新增 `saveConversationData(id, { messages, agentCtx })` 方法，读取现有 JSON、更新 messages 和 agentCtx、写回文件。
  2. `http-server.ts` 新增 `PUT /api/conversation-data/:id` 端点，调用上述方法。
  3. `agentBridge.ts` 新增 `saveConversationData()` 函数，向后端发 PUT 请求。
  4. `ChatView.tsx` 的 `finishStreaming` 中，流式传输完成后调用 `saveConversationData` 将 messages 和 agentCtx 保存到后端。
- **教训**：前后端状态分离后，必须显式设计"前端状态何时回写后端"的时机。流式传输完成（finishStreaming）是自然回写点。

### 4. Settings 页输入字符即失焦

- **现象**：在模型设置页的输入框中输入一个字符，输入框立即失焦，需重新点击才能继续输入。
- **根因**：每次 `oninput` 触发后调用 `props.onChange`，该回调创建全新的 provider 对象（深拷贝 + 修改），导致 `ProviderEditor` 整体重渲染。`<For>` 组件检测到 `models` 数组引用变化，销毁并重建所有子 DOM，输入框被销毁重建自然失焦。
- **修复**：使用 `createStore` 管理本地可变编辑状态（`const [local, setLocal] = createStore({ provider: deepClone(props.provider) })`），输入时直接 `setLocal("provider", "models", mIdx, "id", value)` 就地修改 proxy 属性，不触发整体重渲染。仅在 `handleSave` 时通过 `props.onChange(local.provider)` 一次性提交。
- **教训**：Solid.js `<For>` 对数组引用变化极度敏感——引用变了就销毁重建所有子 DOM。内联编辑场景必须用 `createStore` 本地状态就地修改，不能每次输入都创建新对象。

### 5. deleteConversation 后列表不更新

- **现象**：点击 Sidebar 删除按钮后，conversation 从后端删除成功，但前端列表不刷新。
- **根因**：`deleteConversation` 中使用 `setState('conversations', produce((list) => list.filter((c) => c.id !== id)))`。Solid.js 的 `produce` 包装的是可变 proxy，`filter()` 返回新数组但不会修改原始 proxy，导致 UI 不更新。
- **修复**：改为 `setState('conversations', (prev) => prev.filter((c) => c.id !== id))`，函数式 setState 直接返回新数组替换旧值。
- **教训**：`produce` 适合就地深改（push、splice、属性赋值），不适合返回新数组替换顶层。替换整个数组必须用函数式 setState。

# 如何启动项目？

## 核心概念：三个进程

| 进程 | 代码 | 跑在什么上 | 负责什么 |
|---|---|---|---|
| 前端 | `src/mainview/` | 系统 WebView 或浏览器（开发时连 vite :5173） | Solid.js 软件界面 |
| 桌面壳 | `src/desktop/` | Cottontail（JSC 运行时） | 窗口托管、RPC 本地能力、拉起 Service |
| Service | `src/service/` | Node（开发） / Cottontail（生产）拉起 MTGService.mjs 文件 | Agent 全部业务，监听 HTTP :18999 |

- 前端到 Agent 之间只有 HTTP 一条信道（`127.0.0.1:18999`），与桌面壳无关。
- 前端到桌面壳通过 RPC 通信，实现少量本地能力，与 Agent 无关。
- 桌面壳启动时使用 HTTP 检测后端 Service，如未运行则拉起并托管，否则直接使用已有的 Service。

> 为什么 Service 要单独拆成 node 进程？因为壳所在的 Cottontail 是 JavaScriptCore，inspector 没法在 VSCode 里下断点（排查记录在 docs/调试排查经验-*.md）。想要断点，业务就必须跑在 node 上——这就是三个进程格局的由来。

端口备忘：`5173` = vite dev server；`18999` = Service（HTTP + SSE）；`9230` = 壳的 inspector（JSC，断点不可用）；`9229` = Node inspector（attach 用）。

## 一次性准备

需要 Node ≥ 22、pnpm（`package.json` 已钉 8.15.9）、hutch（安装见 <https://hutch.blackboard.sh>）。

```powershell
pnpm install                # 装 JS 依赖（postinstall 会顺带跑 devkit 补丁用于修复一个类型问题）
hutch electrobun prepare    # 拉 electrobun 2.0.5 devkit 到 .hutch/devkit，新 clone 后必须跑一次
```

Windows 上跑 `hutch run *` 前还得设 `HUTCH_RUNTIME=cottontail`，否则可能会因网络问题而卡住（原因见文末怪规矩表）：

```powershell
$env:HUTCH_RUNTIME="cottontail"    # PowerShell，只对当前窗口有效
# cmd 写：set HUTCH_RUNTIME=cottontail && hutch run dev
# Git Bash 写：HUTCH_RUNTIME=cottontail hutch run dev
```

## 日常开发：两个窗口

**窗口 A：VSCode 按 F5 调试**，选 `Debug Service (:18999)`。preLaunchTask 会先跑一遍 `pnpm build:service`（带 sourcemap）；断点直接打在 `src/service/**` 的 TS 源码上，改完再按一次 F5 即可。

**窗口 B：外部终端**（Windows 上的 VSCode 集成终端会卡住，因此需要外部终端）：

```powershell
$env:HUTCH_RUNTIME="cottontail"; hutch run dev
```

这一条起两路：vite :5173（前端热更新）+ 桌面壳（`--watch`，改 `src/desktop` 自动重编译重开窗口）。

壳启动时先探活 ：18999，通的（你 F5 起的那个）就 adopt，不杀不重启；不通才自己 spawn 一个 Node 进程（注入 `MTG_PARENT_PID` 防孤儿）。所以你在 VSCode 里重启调试服务，桌面壳会自动接上新的那个。

```
VSCode F5 ──▶ node dist/MTGService/MTGService.mjs（:18999，可断点）

外部终端 hutch run dev
 ├─ pnpm run dev:fe ──────────────▶ vite :5173（前端 HMR）
 └─ hutch electrobun dev --watch ▶ 桌面壳
     ├─ 探测 :5173：通 → 连 dev server；不通 → 加载打包产物
     └─ 探活 :18999：通 → adopt；不通 → spawn Service
```

不想动后端、也不想开两个窗口时，可以 `hutch run dev:all` 一条命令全起（前端 + Service watch + 壳三路并行）。但它跟 F5 二选一——同时开会有两路并发写同一个 `dist/MTGService/MTGService.mjs`，Windows 上偶发写坏；而且这模式下改 `src/service` 要重启应用才生效，断点也打不上。

关窗时：壳走完退场动画，只停自己 spawn 的 Service（`POST /api/shutdown` 优雅停机）；adopt 来的调试服务不碰，要你在 VSCode 里停调试会话。

调试不花 token 的办法：Service 起来后开内置 mock，LLM 走假模型、工具照真执行，全链路跑通（用完记得关）：

```powershell
curl -X PUT localhost:18999/api/settings/mock -H "Content-Type: application/json" -d "{\"enabled\":true}"
```

## 命令一览

`hutch.config.ts` 的 `scripts` 是编排层，`package.json` 里的是单点能力，两者不重复：

| 命令 | 干什么 |
|---|---|
| `hutch run dev` | 日常主力：前端 HMR + 壳，不含 Service（vscode 配 F5 调试用） |
| `hutch run dev:all` | 三路全起，不调后端时图省事用 |
| `hutch run start` | 全量构建后启动，无 HMR，验证生产产物 |
| `hutch run build` / `build:canary` | 打 stable / canary 安装包，产物在 `build/<env>-win-x64/`（自解压安装器 + `Resources/<hash>.tar.zst`） |
| `pnpm dev:fe` / `build:fe` | 单起 / 单构前端 |
| `pnpm dev:service` / `build:service` | Service bundle 的 watch / 单次构建，后者就是 F5 的 preLaunchTask |
| `pnpm typecheck` | tsc -b 三个 project（service / desktop / mainview） |
| `pnpm test` | Playwright e2e（需先有 ：5173；浏览器没装过就 `pnpm exec playwright install chromium`） |
| `scripts/patch-devkit.mjs` | 修 electrobun devkit 的 TS4094 回归，postinstall 自动挂，不用手动跑 |
| `scripts/devWindows.cjs` | 在 VSCode 里一键起全套写的绕过方案，用于在 vscode 内也能顺利启动桌面壳 |

## 几条看起来莫名其妙的规矩，都有原因

| 规矩 | 原因 |
|---|---|
| `hutch run *` 必须带 `HUTCH_RUNTIME=cottontail` | hutch 默认 runtime 是 Bun，会先去 GitHub 下 bun 工具链，有可能网络不通；cottontail 已随 devkit 在本机 |
| hutch 脚本里写 `hutch pm exec` 而不是 `pnpm` | hutch 的 shell 不认 Windows 的 `pnpm.cmd` 批处理垫片；`hutch pm` 就是转发给 pnpm 的通道 |
| 别用 VSCode 集成终端跑 `hutch run dev` | 集成终端是 ConPTY，Cottontail 在里面会无输出直接卡死，外部终端一切正常 |
| 停 Service 走 `POST /api/shutdown` | Windows 上 `child.kill()` 等于 TerminateProcess，落盘和 MCP 收尾都不会跑 |
| dev 卡死 / 18999 被占 | 大概率是残留进程：`Get-Process -Name "cottontail","launcher" -ErrorAction SilentlyContinue \| Stop-Process -Force`，必要时清 `.hutch/locks`；用 `/api/health` 返回的 `pid` + `build.gitCommit` 判断占端口的是不是旧代码 |

## electrobun 的心智模型

**electrobun 不太像 Electron，甚至本身不属于前端框架。**

Electron 是焊死的一体化技术栈：主进程是 Node，渲染是自带的 Chromium，包管理天然长在 npm 上。
electrobun 2.x 则把它拆成了几条互相独立的轴：原生核心（窗口 / 菜单 / RPC / 更新）是 Zig 写的；主进程运行时可插拔——可以接 Bun、Cottontail、Zig、Rust、Go，甚至可以完全不需 JS 和 WebView；UI 默认用系统 WebView，不打包浏览器，体积极小。

包管理是另一条独立的轴：hutch 只管原生工具链、devkit 和打包；JS 依赖这一层按 `hutch.config.ts` 里 `packageManager: "pnpm"` 的配置整条委托给了 pnpm——`hutch pm exec vite` 本质就是 `pnpm exec vite`，锁文件也仍是 `pnpm-lock.yaml`。所以 pnpm 不是 hutch 的下层内置工具，而是被 hutch 外包出去的、独立的一层。

本项目就是这套积木的一种拼法：Cottontail 壳 + pnpm 管 JS + Node 跑 Service。顺带提醒一句，Cottontail 不是 Bun——`Bun.file()` / `Bun.spawn` 这些都用不了，得写 `node:fs` / `node:path`。

要本地验证打包产物的话：先把 `Resources/<hash>.tar.zst` 解开，再从 `<app>/Resources/app` 这个 cwd 起 Service（`plugins/`、`mcp-servers/`、`runtime/` 都在那，cwd 起错了就只剩空壳）。

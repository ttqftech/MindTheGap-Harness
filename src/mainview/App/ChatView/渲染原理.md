# 渲染原理速记 —— For / Index / diff 到底在干嘛

> 2026-10-29 讨论沉淀。看 `RenderTree.tsx` 之前先过一遍，能省掉大半疑惑。
> 核心问题只有一个：**页面怎么知道该改哪里**。

## 1. Solid 更新的逻辑：像一份订阅名单

页面首次渲染跑一次组件函数，之后它记住「哪一段文字在盯着哪个数据」。数据一变，只叫醒盯着它的那一小段。

所以 Solid 的「重渲染」是**改一个表达式**，不是重画整个组件。留下的不是虚拟树，而是一堆小监听器：

```jsx
<div class={styles['reasoning-body']}>{sub().content}</div>
//                                 ^^^^^^^^^^^ 就这一小段盯着 sub()
```

`sub()` 变了 → 只把新内容写进**已经存在**的文本节点（`nodeValue`），元素不动。

### 「换对象」和「改字段」不是一回事

- `setTree(新对象)` → 认出来「变了」，通知订阅者。
- `tree.blocks[0].content = 'x'` → **根本没写入任何 signal**，零通知，画面纹丝不动。
- 改完字段再 `setTree(tree)`（同一个引用）→ `===` 判等，照样零通知。

Solid 不做属性级 diff，也没有脏检查。**变化的唯一表达方式是引用变化。** 这就是投影层（`projection.ts`）每次 fold 都造新对象、又用 diff 把没变的部分换回旧引用的原因——前者是让 Solid 知道谁变了，后者是让它别去动没变的地方。

## 2. diff 的行为：沿路径变新，其余原封不动

最深处一段文字变了，会怎样？

```
子 Agent 的 text 子块变了
  → diffSubBlock 返回新对象（它变了）
  → diffBlock(llm)   返回新对象（subBlocks 数组是新的）
  → diffRenderTree   返回新对象（blocks 数组是新的）
```

沿路**每一层对象、每一层数组都是新引用**；但兄弟项（没变的块）仍是旧引用。而且只要某一层判「全等」就 `return old`，**链条到此截断**，上面全保持旧引用，signal 根本不写。

所以「变新」是**一条从叶子到根的细线**，不是整棵树重造。这条线正好喂给 Solid：`createMemo` 只在树引用变了时才通知，通知一次，然后靠 Index/For 的逐项比对把更新收窄到那一格。

开关在 `ChatView.tsx` 的 `ENABLE_RENDER_TREE_DIFF`：

- **开**（现状）：没变的项保持旧引用，什么都不会发生。
- **关**：每帧 fold 出来全是新对象 → `<For>` 判定每一项都换了 → 整列拆了重建（以前「159 个 mutation」就是这么来的）；`<Index>` 不重建元素，但每格都通知一遍，等于丢掉优化白跑表达式。

## 3. For 和 Index：认人 vs 认座位

想象一排椅子：

**`<For>` 认人。** 每个人带身份证（项的**引用**）。还是同一个人，就什么都不做；换了人，就把旧人连椅子一起扔掉、摆把新椅子。中间插进一个人，后面的人只是**挪座位**，椅子跟着人走。

**`<Index>` 认座位号。** 3 号座位永远是 3 号座位，谁坐上去都不换椅子。换人坐只是告诉椅子上的人「你改叫这个名字」，大家原地不动。往中间插一人，后面每个座位的**内容**都跟着变，但椅子不动。

对应到代码里，「箭头函数」就是每个人坐下时干的活：

```jsx
<Index each={node().blocks}>
	{(block, index) => renderBlock(block, isRoot)}
</Index>
```

- `block` 是**函数**（accessor），`block()` 才是当下的值。
- Index：箭头函数**只在多出一个位置时**跑一次；同位置换了对象 → 不跑箭头函数，只是 `block()` 指向新对象 → 读它的表达式重跑。
- For：项的引用变了 → 整格 `dispose()` + 重建 → 箭头函数**重新跑一遍**，子树 DOM、局部 state、`<details>` 展开态全丢。

| | `<For>` | `<Index>` |
|---|---|---|
| key | 项的引用 | 位置下标 |
| 箭头函数收到的 | 值 `(item, i)` | accessor `(item, i)` |
| 同位置换新对象 | 拆掉重建（state 全丢） | 只更新信号，元素不动 |
| 中间插一条 | 后面的项复用 + 挪 DOM，只新建 1 个 | 后面每格都换值（表达式重跑，DOM 不重建） |
| 典型用途 | 会增删/排序、带 DOM 状态的列表（会话列表） | 位置稳定、内容在变的槽（聊天块、工具卡） |

### 铁律：箭头函数要收 accessor

```jsx
{(sub) => <div>{sub().content}</div>}	// ✔ 当场读，订阅生效
{(sub) => { const s = sub(); return <div>{s.content}</div>; }}	// ✘ 建槽时取快照，永久冻住
```

取一次值存着用 = 没人订阅那格信号 = 之后更新全都看不见。**Index + 子函数收 accessor 必须配套。**

### 为什么里面不能写 JS 的 switch

JS 的 `switch` 是**建那一刻**做决定的，建完不再回头。Index 下箭头函数只跑一次，分支定死就永远是首帧那个 DOM。

`<Switch>` 是会一直盯着条件的守门员：条件在「真/假」之间翻转才换分支；条件只是内容变了、但还是「真」，纹丝不动。For 下 JS switch 碰巧没事（整格重建时重新求值），但那是副产品。

## 4. 什么时候两难：中间插入 + 不想重建

Index 的问题：DOM 跟着**位置**走。中间插入后，AskUserCard 的输入框内容、焦点、滚动位置会留在原位，跟错了项（聊天流是追加式的，所以现在没这个问题）。

For 的问题：DOM 跟着**项**走（身份正确），但项一换引用就整格重建——深处分一个字段也全拆，hover 过渡重播就是它。

**两全其美的写法：把身份和内容拆两层。**

```jsx
// 身份层：each 只放 id 数组 —— 只在真正增删时才换引用
<For each={blockIds()}>{(id) => <BlockView id={id} />}</For>

// 内容层：按 id 当场取、当场读
function BlockView(props) {
	return <div>{blockOf(props.id).content}</div>;	// 这行 JSX 表达式订阅 signal
}
```

- id 数组只在增删时变 → For 只建/拆那一格，其他格连箭头函数都不跑，DOM 跟着 id 走。
- 内容更新不碰 id 数组，只写内容 map → 表达式重跑，改文本节点，元素不动。

这就是「For 的身份规则 + Index 的更新粒度」。代价是数据要按 id 可寻址（`Record<id, Item>` 的 signal/map），不能只有一棵树从上往下拿。

### 取值规则（一个就够）

> 响应式读（`sub()` 那一下）必须发生在 JSX 表达式内部；不能在组件体里取一次值存下来。

`sub().a[i].b[j].c` **整条链当场读在 JSX 表达式里就是对的**，不需要每层都变 signal。把 a、b 变成 signal（或用 `createStore`）解决的是**更新粒度**（只重跑最小那段），不是正确性——表达式很短时不必上 store。

## 5. 换到 React / Vue 该怎么想

| | 触发单位 | 跳过手段 |
|---|---|---|
| React | 整个组件函数 | `React.memo`（逆流而上，默认拦不住） |
| Vue | 组件 render effect（patch 按 flag 收窄） | 内建：props 没变的子组件直接 skip |
| Solid | 表达式 | 天生 |

### React 两个常见误会

**`useMemo` 救不了 re-render。** 它在 render 里面跑，等它执行时 render 早就在跑了。能阻止子组件 re-render 的是 `React.memo(Component)`：浅比较 props，`prev === next` 就跳过整个组件。所以叫「逆流而上」——父组件照常重跑，流到被 memo 包住的子组件门口就断了。

**别整表替换，只换那一个。** 规则和 Solid 的引用卫生一模一样：谁变了，谁的那条路径换新引用；没变的一律把旧对象放回去。

```jsx
// ✘ 整表全是新对象，memo 全军覆没
const next = taskList.map(t => ({ ...t }));

// ✔ 只给变了的那个新引用，其余原样塞回
const next = taskList.map(t => t.id === id ? { ...t, meta: { ...t.meta, n: 1 } } : t);
```

深层嵌套用 immer（`produce`）自动做结构共享。

**原地改 `task.a.b.c = xxx` 在 React 里是不可观测的**（Solid 同理）。这不是浅比较的缺陷，是世界观：变化 = 拿到新值。Vue 能行是因为 proxy 拦截了赋值动作。所以二选一：

1. **路线 A（state 在 React 里）**：不可变更新，新引用即信号，配 `React.memo`。
2. **路线 B（数据在 React 外）**：`useSyncExternalStore` / zustand selector 订阅数据源，props 只传 id，prop 不变也照样 re-render。

「给 prop 塞个假 version 字段」能用，但那是手工脏标记，粒度退回整表，是倒退。

### Vue 那边同款优化

`v-for` 遍历稳定的 id 数组、子组件按 id 从响应式对象取数——就是上面「身份与内容分离」。有效的原因是 item 对象引用不再每次 fetch 都换新，props 浅比较放行，兄弟组件零更新。

## 6. 速查

- Solid 更新 = 表达式重跑；换对象才通知，改字段没人知道。
- diff = 沿变更路径造新引用，兄弟保持旧引用，全等就截断。
- For 认引用（身份），Index 认位置（内容）；前者增删排序用，后者流式追加用。
- Index 的箭头函数参数当函数调用（`block().x`），分支用 `<Switch>`。
- 中间插入又想不重建 → id 列表 + 内容 map，别退回纯 For。
- React：`React.memo` 管要不要 render，`useMemo` 只管 render 里省计算；更新靠结构共享，别整表换新。
- 三个框架通用：**把「列表结构变了」和「某项内容变了」表达成两类互不牵连的事件。**
